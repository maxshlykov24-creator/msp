## Зачем три слоя

История двух поломок объясняет схему лучше любого описания.

**7 июля.** Прогон `vault-sync-auto.sh` упал, оставив лок-каталог `logs/.sync.lock`. Лок никто не снимал: следующие прогоны честно писали `skip: locked` и выходили. Так набралось 9304 записи, последний успешный push — 6 июля 22:35. Синхронизация была мертва, но выглядела работающей: агенты в `launchctl list`, лог пишется, ошибок нет.

**13 августа.** Агентов отключили — уже мёртвый механизм лишь закрепили в этом состоянии.

**3 сентября.** Запуск облачного агента. Cursor перед запуском делает `git stash --include-untracked`, чтобы отдать агенту чистое дерево. Стэш забрал весь незакоммиченный слой, накопленный с 19 августа: `_ПРОФИЛЬ/` целиком, системные регламенты, скилл `agent-creator`, документы девяти клиентов, контекст Архитектора. Ветку агента в `main` не влили, стэш не применили — 1235 файлов ушли с диска. Восстановились только потому, что стэш остался локально.

Вывод: опасен не GitHub, а незакоммиченный слой. Пока он большой, любой `stash`, `clean` или `checkout` уносит всё сразу. Поэтому слои закрывают три разные точки: чтобы слой не копился, чтобы стэшу было нечего брать, чтобы поломка не молчала.

## Слой 1 · Снапшот перед задачей агента

Хук Cursor на событие `beforeSubmitPrompt`.

| Что | Где |
|---|---|
| Конфигурация | `.cursor/hooks.json` |
| Скрипт | `.cursor/hooks/vault-snapshot.sh` |
| Лог | `2. БИЗНЕС/08_Системное/Скрипты_vault/git/logs/vault-snapshot.log` |

Перед каждым запросом к агенту, если дерево грязное, делается коммит `Снапшот перед задачей агента: N путей`. Push не делается: промпт не должен ждать сеть, отправку берёт слой 2.

Хук молча пропускает работу, если: стоит `.vault-sync-off`, ветка не `main`, идёт незавершённый rebase, merge или cherry-pick, дерево чистое, лок занят. Любая внутренняя ошибка — тоже пропуск: хук не имеет права мешать работе.

Отключить: убрать блок `beforeSubmitPrompt` из `.cursor/hooks.json`. Проверить, что хук жив: вкладка **Hooks** в настройках Cursor либо канал вывода **Hooks**.

## Слой 2 · Автосинк каждые 15 минут

Два launchd-агента.

| Label | Что делает | Интервал |
|---|---|---|
| `com.msp.vault-sync` | `vault-sync-auto.sh` — commit, pull --rebase, push | 900 сек |
| `com.msp.vault-sync-wake` | `vault-sync-pull-wake.sh` — pull после пробуждения | 300 сек и при логине |

Установка и переустановка:

```sh
cd /Users/max/CURSOR
bash "2. БИЗНЕС/08_Системное/Скрипты_vault/git/install-launchagents.sh"
```

Проверка: `launchctl list | grep msp` — две строки.

Отключение без удаления: `touch /Users/max/CURSOR/.vault-sync-off`. Скрипт проверяет файл и выходит.

Полное снятие:

```sh
launchctl bootout gui/$(id -u)/com.msp.vault-sync
launchctl bootout gui/$(id -u)/com.msp.vault-sync-wake
```

Плюс `post-commit`-хук: твои ручные коммиты уезжают в origin сразу, не дожидаясь агента.

```sh
bash "2. БИЗНЕС/08_Системное/Скрипты_vault/git/install-git-hooks.sh"
```

Проверка: `git config core.hooksPath` возвращает путь к `githooks`. Откат: `git config --unset core.hooksPath`. Разовый коммит без push: `GIT_SKIP_AUTO_PUSH=1 git commit ...`.

## Слой 3 · Контроль живости

Автосинк пишет время каждого успешного push в `logs/last-success`. Если успеха нет больше суток, скрипт кладёт строку `warn` в лог и присылает уведомление macOS, не чаще раза в 6 часов.

Протокол 0 в `3. АГЕНТЫ/CEO/СИСТЕМНЫЙ_ПРОМПТ.md`, пункт 4: агент читает `last-success` и считает `git status --porcelain`. Сутки без push или больше 50 путей вне git — говорит об этом первой строкой ответа, до задачи.

## Что было исправлено в скриптах 2026-09-07

- **Убран `rm -rf`.** `vault-sync-auto.sh` каждый прогон безусловно удалял три legacy-пути, включая `2. БИЗНЕС/99_Системное`, без «да» и без переноса в `99_АРХИВ`. Теперь только предупреждение в лог. Битая ссылка на `99_Системное/Шаблоны/ЭТАЛОН_HTML_ИНСТРУКЦИИ.md` в регламенте Серёжи похожа на след этой чистки
- **Защита от залипшего лока.** Лок старше 30 минут считается мёртвым и снимается. Это лечит поломку 7 июля
- **Heartbeat.** Появился `logs/last-success` и уведомление о сутках тишины
- **Интервал.** 120 → 900 секунд: реже холостых прогонов, история чище, риск потери тот же
- **Потолок ожидания у debounce.** Скрипт не коммитит, пока файлы менялись меньше 90 секунд назад, — это разумно, но при непрерывной правке push не пошёл бы никогда, и снова молча. Теперь ожидание копится в `logs/.debounce-since`, и после 30 минут скрипт коммитит не дожидаясь тишины. Из подсчёта исключены шумные пути (`node_modules`, `.venv`, `__pycache__`, `.pytest_cache`, `dist`, `build`, `.DS_Store`): watcher в них держал бы ожидание вечно

## Диагностика, если push не идёт

1. `tail -20 "2. БИЗНЕС/08_Системное/Скрипты_vault/git/logs/vault-sync.log"` — первое место, куда смотреть
2. `cat .../logs/last-success` — когда последний раз получилось
3. `ls -d .../logs/.sync.lock` — лок должен отсутствовать или быть свежим
4. `ls /Users/max/CURSOR/.vault-sync-conflict` — есть файл, значит `pull --rebase` упал и нужен ручной разбор; после разбора файл удалить
5. `ls /Users/max/CURSOR/.vault-sync-off` — пауза включена вручную
6. `git remote -v` и доступ по SSH: ключ или токен могли протухнуть
7. `.gitignore` закрывает `ДОСТУПЫ*.md`, `.env`, `*.m4a`, `*.mp3`

Логи прогонов: `2. БИЗНЕС/08_Системное/Скрипты_vault/git/logs/`. Копии plist на случай потери: `99_АРХИВ/launchagents/`.
