# Чеклист качества ТЗ (самопроверка @архитектор)

Перед выдачей ТЗ пройди пункты. Если «нет» — доработать или явно пометить как открытый вопрос.

## Бизнес и scope

- [ ] Боль сформулирована и привязана к измеримой цели или к явному качественному результату
- [ ] MVP отделён от Phase 2/3; нет «скрытого» объёма внутри MVP
- [ ] Указано, что категорически нельзя менять (регламент, договор, данные)

## Процессы и данные

- [ ] AS-IS / TO-BE согласованы с таблицами статусов и документов (если ТЗ полное)
- [ ] Для каждого автоматического шага ясен **триггер** и **владелец данных**
- [ ] Маппинг полей содержит типы и обязательность; есть примеры значений

## Интеграция

- [ ] На диаграмме видны amoCRM, МС, middleware (если есть)
- [ ] Описана идемпотентность и защита от дубля webhook
- [ ] Описаны ретраи / dead letter для сбоев API
- [ ] Учтены **лимиты** запросов (см. справочники; при неточности — «уточнить по актуальной доке»)

## amoCRM

- [ ] Названы воронки и статусы **как в продукте**, без абстракций «почти как»
- [ ] Явно сказано: лиды / сделки / customers — что используется
- [ ] Кастомные поля: код/имя, тип, обязательность (если известно)

## «МойСклад»

- [ ] Цепочка документов согласована с учётной политикой клиента
- [ ] Указаны склады / типы цен, если влияют на сценарий
- [ ] Контрагенты: правило матчинга (ИНН, телефон, внешний id)

## Качество текста

- [ ] Нет противоречий между разделами (статусы vs документы)
- [ ] Секреты и токены не вставлены в текст
- [ ] ПДн минимизированы; примеры обезличены

## Финал

- [ ] DoD в конце ТЗ совпадает с тем, что реально можно проверить
- [ ] Открытые вопросы не «прячут» блокирующие решения для MVP
