# Справочник «МойСклад» JSON API 1.2 (выжимка для ТЗ)

**Официальная документация:** https://dev.moysklad.ru/doc/api/remap/1.2/#/general#1-mojsklad-json-api  

Используй как ориентир по **типовым сущностям и цепочкам**; структуру полей и обязательность — сверять с докой и метаданными (`/entity/{type}/metadata`) в проекте клиента.

---

## Базовые принципы API

- **JSON API 1.2**, REST-стиль, сущности по путям `/entity/{type}/...`.
- **Аутентификация:** токен доступа (Bearer) или Basic в соответствии с документацией; секреты в ТЗ **не** писать.
- **Мета и href:** объекты ссылаются через `meta.href`; при проектировании фиксировать, что сохраняем в middleware.
- **Фильтры, `limit`, `offset`, `expand`** — для выборок и вложенных объектов (см. доку).
- **Асинхронные задания** для тяжёлых операций (см. разделы про `task` / async в доке — применимость зависит от операции).

---

## Ключевые сущности

| Тип API (пример) | Назначение |
|------------------|------------|
| **counterparty** | Покупатели / поставщики |
| **product**, **variant**, **service**, **bundle** | Номенклатура |
| **store** | Склад |
| **customerorder** | Заказ покупателя |
| **invoice** | Счёт покупателю |
| **demand** | Отгрузка |
| **paymentin** / **cashin** | Входящие оплаты (по регламенту клиента) |
| **organization** | Юрлицо продавца |
| **project**, **state**, **attributes** | Разрезы и доп. поля |
| **webhook** | Уведомления о событиях в МС |

Точные имена типов и вложенность позиций — по доке для выбранной версии API.

---

## Типовая цепочка продаж (ориентир)

1. **customerorder** — фиксация потребности и состава.  
2. **invoice** — выставление счёта (если ведётся в МС).  
3. **demand** — отгрузка со склада.  
4. Оплаты — документы оплаты по процессу клиента.

Порядок может отличаться (счёт после отгрузки, предоплата и т.д.) — **в ТЗ фиксировать фактический регламент**.

---

## Webhooks

- Подписка на **создание / изменение / удаление** сущностей (см. раздел Webhook в доке).
- Настройка фильтра по типам — снижает шум middleware.

---

## Идемпотентность и внешние ключи

- Для связки с внешней системой часто используют **внешний код** / сохранение соответствия id в своей таблице.
- Повторная доставка webhook или повторный POST без проверки → дубли заказов — в ТЗ явно прописать защиту.

---

## Лимиты и объём

- У платформы есть ограничения по частоте и объёму запросов (см. актуальный текст документации). В ТЗ закладывать **троттлинг, очередь, батч** при массовых синхронизациях.

---

## Типовые ошибки проектирования

- Смешение **заказа, счёта и отгрузки** в один «автоматический шаг» без таблицы статусов.
- Игнорирование **нескольких складов** и резерва.
- Отсутствие стратегии для **частичных отгрузок и частичных оплат**.

## Когда обновлять этот файл

После крупных изменений JSON API или если кейс клиента выявил неточность в выжимке.
