## Обложка

Каркас от идеи до прода: без прыжков в код и петель в дебаге.

Раньше продукт делала команда. Между отделами встречи, тикеты, передача контекста. Полгода от идеи до запуска считались нормой. Запуск шёл из двух источников: CEO или продакт формулировал идею, либо приходил клиент с задачей.

Клиентский путь: клиент → аккаунт → аналитик (ТЗ) → дизайн → разработка → QA → деплой → клиент проверил.

Путь от CEO: CEO → продакт (PRD) → разработка → QA → деплой → пользователи.

В вайбкодинге тот же порядок, но все роли кроме первой берёт один AI-агент. Человек остаётся CEO или клиентом: приходит с запросом и принимает результат. На каждом этапе говорит, в каком отделе агент сейчас работает, и даёт вход: идею, PRD, архитектуру, код.

Проблема: идея, требования, архитектура, причины багов и шаги деплоя живут в голове. На маленьком проекте это держится. Дальше идея за неделю переформулируется и теряется, требований нет и каждый чат стартует с нуля, архитектуры нет и агент пилит не туда, одна ошибка возвращается через два дня, потому что нет правила, которое её ловит.

Шесть шагов. Каждый вытаскивает из головы одну вещь в артефакт: идею в текст, требования в PRD, систему в схему, решения в код, ошибки в правила, запуск в воспроизводимый деплой. На каждом шаге явная роль модели, свой набор инструментов и критерий готовности. Шаги по порядку, но закрытый шаг можно сжать или пропустить.

Порядок: проверка идеи → продуктовая фиксация → архитектура → код → стабилизация → выкладка.

## 1. Генерация идеи

Роль модели: продуктовый стратег. Вытащить идею из головы в текст, к которому можно вернуться завтра, дать прочитать другому и отдать агенту как контекст.

Главный инструмент: голос. На компьютере Wispr Flow, Handy. На телефоне любой чат-бот (GPT, Gemini, Claude). Минуты две надиктовать, как умеешь. Дальше попросить уточняющие вопросы и формулировку.

Цель: идея в тексте.

Шаги:

1. Открыть чат-бот на телефоне, включить голосовой ввод.
2. Запустить интервью: бот задаёт вопросы по одному, ответы голосом.
3. На выходе короткая формулировка и пара историй, как идеей пользуются.

Результаты: формулировка, которую можно скопировать агенту. Истории применения, не детальное ТЗ.

Инструменты: чат-бот с голосом. В Claude Code или Codex библиотека superpowers и команда `/brainstorming`.

Промпт:

> У меня в голове идея: [своими словами]. Помоги её кристаллизовать через интервью. Задай мне 5–7 вопросов с тремя вариантами ответов, по одному. Вопросы задавай строго по одному и дожидайся моего ответа. В конце дай мне структурированный промпт в формате markdown.

Вариант с экспертами:

> У меня в голове идея: [своими словами]. Помоги её кристаллизовать через интервью. Задай мне 5–7 вопросов с тремя вариантами ответов, по одному. С каждым вопросом давай комментарии экспертов, которые могли бы это обсудить, и что бы они сказали — внешний контекст, чтобы я не варился в своей голове. Вопросы задавай строго по одному и дожидайся моего ответа. В конце дай мне структурированный промпт в формате markdown.

## 2. PRD

Роль: продуктовый менеджер. Зафиксировать, что и зачем строишь.

Цель: ЧТО и ЗАЧЕМ, не КАК.

Вход: идея из этапа 1.

Шаги: Purpose (кому и какая ценность), Users и 3–5 сценариев, KPI, constraints (стек, бюджет, время, лицензии), rollout, риски.

Результаты: PRD на 1–2 страницы, таблица KPI. Инструмент: ChatPRD и LLM.

Готово, когда другой человек или модель понимает, что строим, без дополнительных вопросов.

Антипаттерны: писать КАК вместо ЧТО, перфекционизм, игнор constraints.

Промпт:

> Вот идея: [описание]. Создай PRD со следующей структурой: Purpose, Target Users (персоны), User Scenarios (3–5), Success Metrics, Constraints, Risks. Формат: markdown, максимум 2 страницы.

## 3. Архитектура

Роль: программный архитектор. Разложить требования по структуре, данным и контрактам до первой строчки кода.

Цель: КАК продукт работает технически.

Вход: PRD.

Шаги: минимальная архитектура из PRD, стек, структура файлов, data model, API / events / auth / errors / limits.

Результаты: дерево проекта, contracts.md, schema.sql или data_model.md, tech_decisions.md.

Инструменты: Context7 MCP, Sequential Thinking MCP, LLM плюс IDE.

Готово, когда структура файлов создана и можно писать код без архитектурных вопросов.

Антипаттерны: over-engineering для MVP, копировать архитектуру без понимания, игнор constraints из PRD.

Промпт:

> Вот PRD: [вставить]. Предложи минимальную архитектуру. Нужно: 1) Структура папок, 2) Описание каждого файла (1 строка), 3) Data model, 4) Список API endpoints. Стек: [constraint из PRD].

## 4. Код

Роль: разработчик. Небольшие шаги и проверки, не одна простыня.

Цель: минимальный функционал по архитектуре.

Вход: архитектура и PRD для контекста.

Шаги: в контекст PRD, план и структуру. Закрыть тесты задачи. Писать модуль за модулем. После каждого модуля и чанка: проверка, тест, коммит. Потом следующий чанк.

Результаты: рабочий код, базовые тесты, README запуска.

Инструменты: Cursor, Claude Code, Codex.

Готово, когда код написан, тесты проходят, в консоли нет явных ошибок, закоммичено.

Антипаттерны: писать всё сразу, игнорировать ошибки, не коммитить рабочие состояния.

Промпт:

> Роль: Fullstack developer. Задача: [конкретный чанк функционала]. Контекст: [только релевантные файлы]. Когда закончишь — скажи что нужно для следующего.

## 5. Проверка

Роль: разработчик и QA. Воспроизвести, сузить место поломки, проверить гипотезы. Не переписывать всё наугад.

Цель: найти и убрать ошибки систематически.

Вход: код с ошибкой или неожиданным поведением.

Шаги: стабильно воспроизвести, изолировать место, собрать лог, стек и входные данные, сформулировать гипотезу, проверить минимальным изменением, зафиксировать решение.

Порядок: воспроизведи, изолируй, гипотеза, одно изменение за раз, коммит с комментарием что было не так.

Результаты: исправленный код и запись, что было, почему и как починил.

Инструменты: дебаггер IDE, логи, Claude для разбора ошибки, git diff для отката.

Готово, когда ошибка исправлена, добавлен тест, задокументировано.

Антипаттерны: менять всё подряд, не читать сообщение об ошибке, дебажить в проде, не записывать что пробовал.

Промпт:

> Ошибка: [полный текст ошибки]. Как воспроизвести ошибку — среда, тулы и т.д. Код: [релевантный фрагмент]. Что я уже пробовал: [список]. Объясни вероятную причину и предложи 2–3 варианта решения с объяснением, почему каждый может помочь.

## 6. Публикация

Роль: DevOps или разработчик. Сборка, окружение и проверки, чтобы продуктом пользовались без тебя рядом.

Вход: протестированный код и PRD (сверить, что деплоим запланированное).

Шаги: проверить, что PRD выполнен, выбрать платформу, CI/CD если нужно, задеплоить, проверить в проде, мониторинг первых часов.

Результаты: рабочий URL или приложение, инструкция пользователям, алерты на критичные ошибки по желанию.

Инструменты: Vercel, Railway, Render, GitHub Actions.

Готово, когда пользователь открывает продукт без твоей помощи.

Антипаттерны: деплой без тестов, не проверить после выкладки, забыть env, нет отката.

Промпт:

> Проект: [стек]. Нужно задеплоить на [платформа]. Создай пошаговую инструкцию. Укажи: 1) Какие env vars нужны, 2) Команды для билда, 3) Как проверить что работает, 4) Как откатить если сломается.
