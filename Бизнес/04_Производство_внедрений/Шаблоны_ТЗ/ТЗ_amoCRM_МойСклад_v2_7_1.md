## **0.2. amoCRM — чек-лист работ (4 задачи)**

### **Задача 1: Настроить webhook**

В amoCRM: Настройки → Интеграции → Webhook. Указать URL сервера DETENSOR Analytics (получить у разработчика). Активировать 5 событий:

* Создание сделки

* Изменение сделки (этап, бюджет, ответственный)

* Смена этапа сделки — главное событие

* Удаление сделки

* Создание/изменение контакта

→ Детали: раздел 5 «amoCRM — настройка webhook»

### **Задача 2: Передать API-токен разработчику**

Создать долгоживущий access\_token в amoCRM (Настройки → Интеграции → создать или взять существующую интеграцию). Права: чтение сделок, чтение контактов. Передать токен разработчику ИСКЛЮЧИТЕЛЬНО через защищённый канал (личное сообщение, не общий чат).

Также записать: Account ID amoCRM (Настройки → Профиль аккаунта → ID).

### **Задача 3: Подтвердить корректность полей анкеты**

В разделе 4 указаны все 13 полей анкеты с реальными Field ID из выгрузки. Нужно проверить:

* Все 13 полей доступны менеджерам во ВСЕХ 7 воронках (а не только в Обращениях)

* Поле «Диагноз» (Field ID 3032499\) имеет 10 значений — менеджер может выбрать конкретный диагноз, а не только Есть/Нет

* Поле «Маршрут клиента» (3032853) появляется на этапе квалификации в Обращениях

* Поле «Был на пробной» (3026309) появляется в воронке Пробная процедура

Если каких-то полей не хватает или они недоступны — добавить их в карточку соответствующей воронки.

### **Задача 4: Дубликаты полей — проверка истории**

В amoCRM есть 7 пар дубликатов полей (старые/новые версии — см. раздел 4.4). Нужно проверить:

* Есть ли в исторических сделках данные в СТАРЫХ полях (3024254 Возраст, 3024256 Вес и т.д.)

* Если есть — обсудить с заказчиком стратегию миграции этих данных в новые поля (3032517, 3032519 и т.д.)

# **1\. Введение и цели проекта**

DETENSOR — компания продающая ортопедические массажные маты для лечения проблем со спиной. Все продажи ведутся через amoCRM (2 менеджера), товары и склад — в системе МойСклад.

Цель проекта: подключить к дашборду analytics.detensor.ru два источника данных: amoCRM (сделки, этапы, поля анкеты, менеджеры) и МойСклад (товары, остатки, продажи). Сейчас дашборд готов и работает на демо-данных — задача исполнителя обеспечить поток реальных данных в БД сервера.

Архитектура решения:

amoCRM ──webhook (POST)──┐                         ├──► PHP-обработчик ──► MySQL ──► Dashboard (HTML)МойСклад ──API (cron)──────┘

*ВАЖНО: разработчик сервера и БД — отдельный исполнитель. Эта задача — про настройку amoCRM, МойСклад и согласование структуры передаваемых данных (JSON-контракт). Серверную часть пишет другой человек.*

## **3.5. Особенность воронки «Аренда» (выкуп после аренды)**

По уточнению заказчика: когда клиент выкупает мат после аренды — это НЕ создание новой сделки в воронке «Заказы», а ДОБАВЛЕНИЕ ВТОРОГО ТОВАРА в существующую сделку аренды. То есть:

9. Клиент берёт «Аренда 28 дней Ж2» (9 900 ₽) — сделка в воронке «Аренда» (Pipeline 9033890\)

10. Через месяц решает купить мат — менеджер ДОБАВЛЯЕТ к этой же сделке товар «Мат-DETENSOR Ж2 (без валика)» (63 300 ₽)

11. Сумма сделки \= 9 900 \+ 63 300 \= 73 200 ₽

12. Сделка переходит на этап Stage 142 (Успешно реализовано \= Выкуп)

*Логика для дашборда: сделки воронки «Аренда» где есть 2+ товара (услуга аренды \+ физический товар) \= выкуп. Сделки где только услуга аренды \= просто аренда. Это нужно отразить в обработчике webhook.*

Дополнительная защита: даже если канал продаж не «Розница», сделка учитывается только если поле responsible\_user\_id равно одному из 3 разрешённых User ID:

## **7.А.2. Найденные проблемы в каталоге**

### **Проблема 1\. Артикулы устроены задом наперёд**

Сейчас:

* Поле «Артикул» (основное) — содержит ПОЛНОЕ НАИМЕНОВАНИЕ товара (пример: «Ночной матрас FIBROTOP MAX 80 \* 200 \* 18»)

* Доп. поле «Артикул» — содержит РЕАЛЬНЫЙ бизнес-артикул (пример: FBM80)

При выгрузке через API сервер будет читать основное поле и получать длинное название вместо короткого кода. ЗАДАЧА: поменять местами эти поля для всех 128 целевых SKU.

### **Проблема 2\. Жёсткость не хранится отдельным полем**

Сейчас закодирована в артикуле:

* Маты Детензор: D18H00 (Ж0), D18H01 (Ж1), D18H02 (Ж2), D18H02P (Ж2+), D18H03 (Ж3)

* Матрасы Fibrotop Classic: суффиксы \-1 (Ж1) и \-3 (Ж3), без суффикса \= базовая Ж2

* Аренда: rent28\_m1 (Ж1), rent28\_m2 (Ж2), rent28\_m2+ (Ж2+), rent28\_m3 (Ж3)

ЗАДАЧА: создать доп. поле «Жёсткость» в МойСклад и заполнить его для всех 41 SKU (17 матов \+ 14 Classic \+ 9 Max \+ 12 аренда).

### **Проблема 3\. Названия товаров — одинаковые «Устройство медицинское DETENSOR...»**

У \~50 SKU название обрезано и одинаковое. В дашборде во вкладке «Товары» будут визуально одинаковые карточки. ЗАДАЧА: переименовать в человечные названия. Примеры:

## **7.В.2. Особый случай: воронка Аренда — связка двух товаров в одной сделке**

По уточнению заказчика — выкуп после аренды это НЕ новая сделка, а добавление второго товара в существующую сделку аренды. Пример последовательности:

Этап 1 (Аренда взята):  Сделка \#12345 в воронке «Аренда»  Товар: «Аренда лечебного мата Детензор 18% на 28 дней (жесткость 2)» — 9 900 ₽  Этап: «Передан клиенту»Этап 2 (Клиент решил выкупить):  В ту же сделку \#12345 добавляется второй товар:  «Мат-DETENSOR — Жесткость 2 (без валика)» — 63 300 ₽  Сумма сделки \= 9 900 \+ 63 300 \= 73 200 ₽  Этап: «Оплата получено» (= Выкуп)Для дашборда:  — Сделка попадает в воронку «Аренда»  — Если в товарах сделки только услуга аренды → это «обычная аренда»  — Если в товарах есть и услуга аренды И мат → это «аренда с выкупом»

*Это критично для правильного подсчёта выручки в дашборде. Разработчик сервера должен в обработчике webhook проверять состав товаров каждой сделки воронки «Аренда» и помечать тип сделки (только аренда / аренда+выкуп).*

## **9.2. Поле анкеты «Откуда узнали о DETENSOR»**

Это поле №13 из анкеты клиента (см. раздел 4.2). Заполняется менеджером ВРУЧНУЮ в момент квалификации, на основе ответа клиента на вопрос «Подскажите, откуда вы о нас узнали?». Это полностью отдельный параметр от UTM-меток — он отражает ИСТОЧНИК ЗНАНИЯ О БРЕНДЕ (где клиент впервые услышал о DETENSOR), а не рекламный канал последнего перехода.

| № | Вариант (radio-список) | Когда выбирается |
| :---: | ----- | ----- |
| 1 | **Рекомендация — Врач** | Клиента направил врач (невролог, терапевт, ортопед, мануальный терапевт) |
| 2 | **Рекомендация — Друг/Родственник** | Кто-то из знакомых уже пользовался DETENSOR и порекомендовал |
| 3 | **Реклама в интернете** | Увидел рекламу в Яндекс/Google (общий вариант, не привязан к UTM) |
| 4 | **Телеграм** | Узнал из Телеграм-каналов |
| 5 | **Соц.сеть** | Увидел в VK / Instagram / Facebook / YouTube |
| 6 | **Санаторий** | Попробовал в санатории, где стоит оборудование DETENSOR |
| 7 | **Свой вариант** | Если клиент назвал источник который не входит в список |

*Это поле — ПРИОРИТЕТНЫЙ источник правды для блока «Как о нас узнали» в дашборде. UTM-метки (ДКТ: Источник) — это техническая метка последнего перехода и НЕ показывают где клиент УЗНАЛ о бренде. Пример: клиент впервые услышал о DETENSOR от врача, потом загуглил и пришёл через рекламу Яндекс. UTM покажет «yandex», но реальный источник — «Врач».*

## **9.3. Как эти поля используются в дашборде**

### **Профили клиентов → блок «Как о нас узнали»**

Использует поле анкеты №13 (раздел 9.2). 7 вариантов ответа \= 7 строк в блоке.

### **Будущая вкладка «Маркетинг» (опционально)**

В перспективе можно добавить отдельную вкладку с аналитикой по автоматическим полям (раздел 9.1):

* Распределение заявок по «Источник сделки» (Заказ vs Заявка vs Jivo)

* Распределение выручки по «Канал прод.» (Розница vs Опт vs Партнёрка)

* Эффективность рекламных кампаний по «ДКТ: Кампания» (ROI по кампаниям Яндекс/Google)

Этот блок — за рамками текущей задачи, но данные для него собираются уже сейчас.
