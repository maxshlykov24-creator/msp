# Базовые настройки amoCRM (чеклист гигиены)

> Применять на каждом новом проекте до начала нишевой настройки.
> Проверено на практике (Linderwood, 2024).

---

## Блок 0 — Настройки вне воронок

| # | Настройка | Зачем |
|---|-----------|-------|
| 0.1 | **Запрет удаления неразобранного** | Исключает потерю заявок |
| 0.2 | **Цветные теги** | Быстрая визуальная навигация |
| 0.3 | **Запрет сделок без задач** | При наличии сделки без задачи — всплывающее окно на каждой странице; при работе внутри сделки — не дать выйти без постановки задачи |
| 0.4 | **Запрет на удаление / редактирование задачи** | Фиксирует факт постановки; обязательный результат при закрытии |
| 0.5 | **Скрытие полей и вкладок по воронке** | Меньше визуального шума, меньше ошибок |
| 0.6 | **Вкладка «Все сделки» внутри сделки** | Видны все связанные сделки компании в одном месте |
| 0.7 | **Перенос строк в названиях полей** | Полное отображение длинных названий без обрезки |
| 0.8 | **Переход в сделку при обязательных полях** | Не дать закрыть сделку с незаполненными ключевыми полями |
| 0.9 | **Сохранение выставленных фильтров** | Фильтр держится до ручного сброса |
| 0.10 | **Отображение времени на этапе** | Видно, сколько сделка «зависла» на этапе |
| 0.11 | **Красная подсветка при 21 дне без действия** | Визуальный сигнал о брошенных сделках |
| 0.12 | **Кнопка-счётчик в числовых полях** | Удобное накопление значений без ручного ввода суммы |

## 6 правил работы с воронкой

Проверено на практике (Mansband, 2025). Вводить клиенту как обязательный регламент перед запуском.

1. На каждом этапе — фокус только на **цели этапа**. Цель выполнена — переводить на следующий.
2. Не допускать выход сделки из **сроков этапа**. Сделка потеряна без контроля сроков.
3. Работать только через **задачи** в сделке. Без задачи — нет следующего шага.
4. К каждой задаче — **комментарий**: Что сделал — Ответ клиента — Следующие действия.
5. **Запрещено удалять задачи** и редактировать дату. Завершать только с комментарием + новая задача.
6. Поля, этапы и задачи — **сразу по факту**, не откладывать.

## Паттерн эскалации задач

Универсальная логика контроля: менеджер получает сигнал первым, руководитель — если менеджер не среагировал.

### Обработка новой заявки

| Время | Действие |
|-------|----------|
| Заявка поступила | Уведомление всему отделу продаж |
| +10 мин без принятия | Повторное уведомление отделу |
| +20 мин без принятия | Задача на **руководителя** |
| Принята, +2 ч без движения | Задача менеджеру: перевести в нужную воронку |
| Принята, +3 ч без движения | Задача **руководителю** |

### Этап «Взято в работу / КП отправлено»

| Время | Действие |
|-------|----------|
| +1 день | Задача менеджеру: взять обратную связь |
| +2 дня | Задача менеджеру: перевести или закрыть |
| +3–5 дней | Задача **руководителю** |

### Стагнация в воронке

| Время | Действие |
|-------|----------|
| 7 дней без движения | Задача менеджеру |
| 21 день без движения | Задача **руководителю** |
| Подсветка сделки красным | Автоматически при 21 дне без действия |

## Чеклист мультиканальной интеграции

Проверено на практике (Mansband, 2025). Применять для ретейла и любого бизнеса с многоканальным входящим потоком.

| Канал | Что интегрируем | Приоритет |
|-------|-----------------|-----------|
| Телефон + calltracking | Звонки в amoCRM, автоопределение источника по UTM | Обязательно |
| WhatsApp | Личный + рабочий номер → переписка в сделке | Обязательно |
| Telegram | Личные сообщения + канал/сообщество → сделки | Обязательно |
| Instagram | DM + комментарии → сделки | Обязательно |
| ВКонтакте | DM + комментарии → сделки | Обязательно |
| СДЭК | Автоотслеживание статуса доставки по треку | Обязательно |
| Сайт / онлайн-чат | Форма с захватом номера телефона | По необходимости |
| Яндекс.Карты / 2ГИС / Google | Отзывы → уведомление или сделка | Под вопросом у клиента |

**Важно при мультиканале:**
- Автоматически проставлять источник заявки (UTM + calltracking) — без этого аналитика по каналам не работает
- Разделять: источник (откуда пришёл) vs способ связи (как общаемся) vs куда пишут (какой аккаунт) — объяснять клиенту разницу
- Отдельная воронка или этап для справочных звонков (открытие ворот, не целевые)

## Дополнительные модули (продаются отдельно)

### Дожим через кассу
Проверено на практике (Mansband, 2025). Для ретейла с физическими точками.

**Как работает:**
- Консультант в магазине фиксирует через кассу: клиент ушёл без покупки → статус **Ушёл смотреть у конкурентов** или **Не оказалось размера**
- К сделке привязывается имя консультанта (чтобы он был заинтересован в дожиме)
- Кассир фиксирует провалы + причины + номера телефонов ‼️
- Отдельный этап **«Можно дожать»** → сделка уходит кол-менеджеру для дожима
- Анкеты по коллекции / причинам ухода → аналитика для ассортимента

**Когда предлагать:** любой ретейл с консультантами и онлайн-менеджерами.

---

### Совместные продажи (несколько точек)
Проверено на практике (Mansband, 2025). Для ретейла с 2+ магазинами.

**Как работает:**
- Ответственный за заказ = тот, кто завершил продажу
- Второй консультант (который направил клиента из другого магазина) — в поле **Второй ответственный**
- Оба получают % с продажи
- При продаже/доплате за чужую отложку — % получает тот, кто отложил

**Когда предлагать:** ретейл с несколькими точками, франшизы, шоурумы.

---

### Реферальная программа
Проверено на практике (LookBook, 2024). Реализуется внутри amoCRM без сторонних сервисов.

**Как работает:**
- При нажатии кнопки менеджер делает клиента **рефером** — в карточке контакта автоматически создаётся персональная реферальная ссылка
- Отдельная воронка **Рефереры** — видны все клиенты, участвующие в программе
- При регистрации нового клиента по ссылке — сделка автоматически привязывается к рефереру
- При успешной сделке реферала — уведомление рефереру о начислении бонуса
- Бонусы накапливаемые; логика начисления настраивается под клиента

**Когда предлагать:** любой бизнес с повторными продажами и лояльной базой клиентов.

---

### Воронка повторных продаж для сервисного бизнеса
Проверено на практике (LookBook, 2024). Работает для студий, агентств, любого сервиса с разовыми сделками.

**Структура воронки «Покупатели»:**
1. Услуга оказана → сделка попадает в воронку автоматически
2. **+1 месяц** → задача менеджеру: повторное касание
3. **+2 месяца** → задача менеджеру: повторное касание
4. Теги сегментации по объёму/частоте покупок

**Отличие от товарного бизнеса:** нет «отгрузки» и «остатков» — логика строится вокруг даты оказания услуги.
