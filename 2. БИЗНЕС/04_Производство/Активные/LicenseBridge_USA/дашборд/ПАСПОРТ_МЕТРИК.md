## 2. Причины отказов по источникам и менеджерам — блок клиента

### 2.1 Общая диаграмма причин отказа

**Статус: ⚠️ Допущено с обязательным индикатором полноты.**

- В основной воронке 1229 сделок закрыты как lost. У **718 (58,4%)** причина отказа **не указана**.
- Из указанных 511 — **186 (36%)** это «другое» (неинформативно).
- Реально диагностических причин (пропала потребность / дубль / неверный номер / заказал у конкурента / не устроила стоимость / не устроили сроки / спам) — **128, то есть 10,4% от всех отказов.**
- **Решение:** показывать диаграмму только по факту заполненных причин, обязательно с крупной подписью «указана причина у X% отказов» и не давать читать долю как «причина №1 — пропала потребность у 58 сделок» без контекста, что это 4,7% от всех отказов, а не 47%.

### 2.2 Источник → доля нецелевых лидов

**Статус: ⚠️ Допущено комбинированно (переаудит 2026-07-22); разрез «источник → нецелевые» — только после чистки Channel.**

- Поле `Channel` заполнено у **6,7%** (110/1634); реальный источник без `да/нет` — **1,35%** (22).
- `utm_source` — **1,6%**; `ttad_name` — 0%.
- Теги есть у **79,8%**; из них source-like (`FB`, `fb…`) дают основной сигнал.
- **Комбинированный best-source** (Channel real → utm → FB-тег): покрытие **64,8%** (1059/1634). Без тегов ≈ **2%**.
- **Вывод:** «источник неизвестен» в Channel — правда про поле; по тегам Facebook Ads виден у большинства. В прототипе — топ комбинированных значений + честная подпись про Channel 6,7%.

### 2.3 Менеджер чаще теряет клиентов

**Статус: ⚠️ Допущено только с event-коррекцией и только за недавний период; общая история — исключена.**

Наивный расчёт «отказы по текущему `responsible_user_id`» дал бы **грубо неверную** картину:

| | Наивный расчёт (по текущему полю) | Восстановлено по событиям (кто реально был ответственным на момент `closed_at`) |
|---|---|---|
| Илона | 1152 (94% всех отказов) | 152 |
| Pavel | 77 | 61 |
| Бывшие сотрудники (уже не в Kommo) | 0 | **1016 (82,7%)** |

- Причина: массовые переназначения (3431 событие `entity_responsible_changed` за 14 месяцев). У **82,8%** потерянных сделок основной воронки текущий ответственный не совпадает с тем, кто фактически вёл сделку в момент отказа.
- Даже если смотреть только последние 60 дней (407 отказов) — несовпадение **71%**, потому что переназначения продолжаются регулярно, а не были разовой миграцией.
- **Решение:** (1) в дашборде считать «ответственного на момент отказа» строго через историю событий `entity_responsible_changed`, а не текущее поле; (2) показывать разрез по менеджерам только за период после стабилизации команды (нужно зафиксировать с клиентом дату, ориентировочно после последнего массового переназначения); (3) явно подписывать, что данные до этой даты относятся к сотрудникам, которых уже нет в команде, и не подходят для оценки текущих менеджеров.
- Дополнительно нормировать как `lost / (won + lost)` в одной когорте по дате закрытия — не наказывать за больший объём лидов (заложено в план).

### 2.4 На каком этапе чаще происходит потеря клиента

**Статус: ✅ Допущено · в дашборде с 2026-08-03.**

- События `lead_status_changed` доступны в Kommo с полной историей (проверено наличие событий помесячно с 2025-06 по 2026-07 включительно) — можно восстановить предыдущий этап перед переходом в lost для каждой сделки, без искажений от переназначений (эта метрика не завязана на пользователя).
- В live-дашборде (вкладка РОП): блок **«Где теряются»** — `lost_from_stage` (этап перед status 143) по дате закрытия, доля от отказов периода. Линейную конверсию «этап → этап» не показываем: лиды входят с разных этапов и прыгают, проценты между полосками врют. «Сделки по этапам» выше — снимок открытых (очередь).

## 4. Дополнительно найдено аудитом (не входило в запрос клиента, но важно)

- **Смена состава команды в Kommo.** Лилия, Лэйла, Светлана, Алина — больше не пользователи аккаунта. Сейчас: Pavel, Полина, Илона (похоже на менеджеров) + Максим, Дмитрий (админы — роль не ясна, вероятно техническая/подрядчик; **нужно уточнить у клиента**, чтобы не показывать их в разрезах по менеджерам как «продажников»).
- **93% лидов основной воронки сейчас закреплены на Илоне** — результат переназначений, не реальное распределение работы; сам этот факт стоит показать клиенту как операционный риск (бас-фактор на одного человека), а не как метрику эффективности.
- **`Won` в основной воронке** с 26.08.2026 считаем по переходу в Closed-won (status 142) внутри Pipeline. Раньше (до согласования с Павлом) в дашборде была гипотеза «выигрыш = переход в Сборку». Сборка осталась метрикой «В производстве». История 142 до августа 2026 почти пустая — на KPI подписано, с какой даты метрика сопоставима.
- **Индикатор качества данных** (предложение к добавлению, единственное сверх запроса клиента): компактный блок «доля сделок без источника / без причины отказа / без задачи / с корректным ответственным» — объясняет пользователю дашборда, почему остальные цифры выглядят именно так, а не даёт ложное ощущение полноты.
