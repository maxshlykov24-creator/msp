## 7а. Веб-интерфейс TG400 (проверено 2026-07-27)

Полный опыт IVR/лимит 1 call / Playwright: [`ОПЫТ_ТЕЛЕФОНИЯ_ASTERISK_TG400.md`](ОПЫТ_ТЕЛЕФОНИЯ_ASTERISK_TG400.md).

Туннель с Mac mini → `http://127.0.0.1:8081`, вход `admin` / `password`
(стандартный, сменить — см. §11.2). Пароль уходит на сервер не открытым текстом:
интерфейс считает MD5, кодирует в base64 и сдвигает каждый символ на +2, поэтому
логин обычным `curl` без повтора этой схемы не проходит. Сессия одна: при
автоматическом входе браузерная выкидывается, и наоборот. Автоматизация UI —
через **Playwright/Chrome** (cookie считает JS), не через голый curl.

**Второй набор.** Пустое поле `Hotline` в маршруте Routes → Mobile to IP
означает, что шлюз сам ответит на входящий и будет ждать донабора тоном, до
Asterisk такой звонок не дойдёт. В маршрутах должны стоять `1001` / `1002` /
`1003` (см. `asterisk/README.md`). `Simple Mode` к этому отношения не имеет —
он лишь прячет шаблоны номеров и Callback.

**Идентификация входящего SIP.** TG400 передаёт внешний CallerID в заголовке
`From`, поэтому Asterisk нельзя полагаться только на `username`: получится
`No matching endpoint`, затем `401`, а шлюз отметит вызов как `FAILED`. В
`/etc/asterisk/pjsip.conf` для трёх TG400-endpoint включено
`identify_by=auth_username,username`, глобальный порядок —
`auth_username,username,ip,anonymous`. Так после digest-челленджа транк
определяется по логину `Authorization`, а номер звонящего сохраняется как CLIP.

## 9. Что нельзя менять без плана отката

- Не менять TG400 `192.168.5.150`, маску, шлюз `192.168.5.1` и DNS без одновременного обновления Mac mini и relay.
- Не отключать на Mac mini `Remote Login`, `Remote Management`, Wi‑Fi или Ethernet.
- Не удалять два LaunchDaemon, SSH-ключи, PF-anchor и watchdog.
- Не включать шлюз на Ethernet Mac mini: основной интернет должен оставаться через Wi‑Fi `en1`.
- Не открывать VNC, SSH Mac mini или TG400 на роутере AT&T.
- Не применять общий `/etc/pf.conf` через `pfctl -f` без проверки динамических правил Internet Sharing; TG400 использует отдельный anchor.
- Не восстанавливать backup `before` без возврата старой сетевой схемы.
- Не пересоздавать контейнер relay вслепую: сначала проверить persistent keys и валидность нового образа.
- **Не включать SSH на TG400** (`System → Security Center → Enable SSH` + Apply) без явного ОК пользователя и человека в США на power cycle. 27.07.2026 после этого шлюз выглядел «мёртвым» (нет ping/HTTP; Mac mini жив). **Уточнение 28.07:** шлюз не зависал — его защита забанила IP Mac mini за серию SSH-коннектов на порт `8022`, см. `ОПЫТ_ТЕЛЕФОНИЯ_ASTERISK_TG400.md` §1.5е. Штатный доступ — только HTTP через туннель `http://127.0.0.1:8080` + Playwright.
- **Не удалять правило фаервола `LAN_MacMini_Accept`** в TG400 (`Firewall Rules`: ACCEPT, BOTH, порты `1:65535`, IP `192.168.5.1`). Оно добавлено 28.07 и защищает управляющий адрес Mac mini от автобана. Без него любая серия запросов к шлюзу снова кладёт доступ.

## 9а. Если шлюз «не отвечает» (28.07.2026)

Сначала проверить бан, только потом думать про железо и питание:

```bash
ssh -p 10023 pavelkhlopenko@127.0.0.1 \
  'curl -s -o /dev/null -w "обычный:%{http_code}\n" --max-time 6 http://192.168.5.150/;
   curl -s -o /dev/null -w "другой source:%{http_code}\n" --max-time 6 --interface 192.168.1.83 http://192.168.5.150/'
```

- `обычный:000` + `другой source:200` → **бан IP `192.168.5.1`**: снять запись в
  `Security Center → IP Blacklist`, проверить наличие правила `LAN_MacMini_Accept`.
- Оба `000` при живом ARP → шлюз действительно не отвечает, тогда power cycle.
- Обходной прокси на время бана — `ОПЫТ_ТЕЛЕФОНИЯ_ASTERISK_TG400.md` §1.5е.
