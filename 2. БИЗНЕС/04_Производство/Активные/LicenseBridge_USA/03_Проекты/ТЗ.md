## 1. Цель проекта

Сделать Kommo управляемой sales-системой, где лид из любого источника доходит, автоматически назначается на менеджера, не теряется в дублях, ведётся по задачам и времени этапов, а РОП видит ключевые метрики на дашборде без ручных отчётов.

**Границы (что НЕ входит):** AI/нейро-сотрудники, автодозвон по B2B-базе, автогенерация КП/договоров, автоссылки на оплату, транскрибация звонков. Эти пункты — отдельные проекты после базового контура.

## 6. Этап 1 — связь, лиды, распределение (6–7 дней)

**Цель:** менеджеры стабильно общаются с клиентами в мессенджерах, лиды доходят и распределяются, звонки фиксируются в CRM.

**Порядок работ (приоритет уточнён на созвоне 18.06):**
`1) мессенджеры → 2) приём лидов → 3) распределение → 4) телефония → 5) дубли`

### 6.1 Мессенджеры — белая (официальная) интеграция WhatsApp / Telegram — ПРИОРИТЕТ №1
- Перевести WhatsApp (и при необходимости Telegram) на официальную интеграцию вместо серой через e-chat.
- Снять зависимость от личного телефона Павла: сейчас связь по QR (одно устройство); при отвале VPN/интернета в РФ менеджеры весь день не могут отправлять КП/файлы. Официальный канал работает как отдельный аккаунт, не привязанный к устройству.
- Проверить отправку файлов/КП и доставляемость первого сообщения.

### 6.2 Приём лидов
- **Facebook через Make.com**, а не прямую интеграцию: подключить несколько рекламных аккаунтов параллельно (резерв при бане/проверке одного) через готовые ноды Facebook Lead Ads и Kommo API, обходя долгую верификацию собственного Meta App.
- Tilda → Kommo через API/вебхук: создание сделки в `Pipeline` (`11274779`) с контактом, телефоном, источником и UTM. Убрать ручной перенос файлом/через новый лид.
- Свести Meta forms, Instagram, TikTok, Google в единую логику. Источник писать в `Channel` (`143104`), UTM-поля, `ttad_id` (`1408266`).
- Проверить роль ApexDrive vs Teletype, исключить дубли каналов.
- Авторизовать Facebook/Instagram, чтобы доходили комментарии к рекламным постам.
- SMS RingCentral: проверить нестабильность (ограничения по объёму текста и частоте сообщений).

### 6.3 Распределение
- Автораспределение новых заявок по правилу. **Учитывать часовые пояса:** менеджеры работают день/ночь, покрывают Нью-Йорк и Калифорнию; клиент назначается на менеджера в подходящем поясе. Точное правило фиксируется на старте.
- Минимизировать роль `Неразобранное` (`86527435`): лид попадает сразу на `Первичный контакт` (`86527439`) с ответственным.
- Передача сделки между менеджерами — только при выявлении дубля; иначе клиент закреплён за одним менеджером.

### 6.4 Телефония (RingCentral + SIP)
- Привязать/починить линии менеджеров, в первую очередь **Алины** (`15380172`, 0 звонков в CRM — уже сопоставлена в RingCentral и Kommo, проблема глубже в интеграции) и **Светланы** (`15289896`, частично). Цель — чтобы ни один звонок не терялся.
- Проверить логирование входящих/исходящих и записи в карточку (запись для РОПа — важно, но не первостепенно).
- SIP-оборудование: настроить прямой удалённый доступ к оборудованию через роутер (не через компьютер/AnyDesk) для перезагрузки при отвале регистрации SIM. RingCentral оставить резервом на ~2 месяца, пока модель не стабильна.

### 6.5 Дубли и повторы
- Объединение/проверка дублей на стороне сервера (а не платными виджетами) — у клиента нет сложных интеграций. Отдельно продумать Instagram (часто известен только ник).
- Закрепить правило «новая сделка только если у клиента нет активных сделок» (любая воронка).
- Снять костыль «контакты открыты всем»; настроить корректные права + видимость, что клиента уже ведёт другой менеджер.

**DoD этапа 1:**

## 7. Этап 2 — задачи, сроки, дисциплина (4–5 дней)

**Цель:** у каждой активной сделки есть следующий шаг, этапы контролируются по времени.

- Правило «нет сделки без задачи»: виджет/механизм, блокирующий сделку без поставленной задачи (клиент готов ставить).
- Контроль просрочек: цель — каждый день без просрочек (допустимо 1–2 дня в небольшом объёме). Сейчас 46 просрочек, 38 на Алине — разобрать (часть — повторные/непривязанные задачи холодного прозвона, см. чистку ниже).
- **Уведомления о застое в Telegram-чат:** бот в чате тегает ответственного менеджера и даёт ссылку на застрявшую сделку (переход прямо в карточку), не только автозадача. Если менеджер не двигает — подключается РОП, чтобы закрыть историю.
- **Памятки к этапам уже есть** у клиента в настройках воронки (автоматизация) — забрать их как основу для целей и SLA этапов; время по этапам клиент пришлёт текстом/голосом (отдельный созвон не обязателен).
- Чистка мусора: удалить тестовые сделки и непривязанные задачи холодного прозвона (≈40 контактов).
- SLA по времени на этапах основной воронки — нормы согласуются с РОПом, ориентир:

| Этап | id | Норма (ориентир) |
|------|----|------------------|
| Первичный контакт | `86527439` | первичная реакция в течение N минут/часов |
| Квалификация | `96943275` | до N дней |
| В работе | `106419976` | до N дней |
| Выставлен счёт | `86527447` | до N дней, контроль оплаты |
| Прогреваю/Отложенный спрос | `96943279` | периодический пуш раз в 2–3 мес. |

- Возврат «Прогрева» (`96943279`, сейчас 137 сделок) в работу: при ответе клиента/по таймеру сделка возвращается в `В работе` (`106419976`) с задачей.
- Подключить личные рабочие email менеджеров.
- Шаблоны email/SMS/WhatsApp для типовых касаний.

### 7.1 Стыковка продажа → Сборка
- При переходе сделки в won в `Pipeline` автоматически заводить сделку в `Сборка` (`12079591`) на стартовый этап (`Заполняют анкету` `93231787`) с переносом контакта и сохранением истории переписки/примечаний.
- Закрыть текущую практику «держим won-сделки незакрытыми ради истории» — это ломает аналитику конверсии.

**Реализация (2026-07-24):** без Salesbot — на нативном вебхуке `status_lead`,
который hub уже обрабатывает (`app/handoff.py`, план `handoff_pipeline_to_sborka`).
История сохраняется backdate’ом `created_at` новой сделки на дату исходной — лента
Kommo подтягивает прежние звонки/чаты контакта в карточку (±24ч от `created_at`,
подтверждено поддержкой Kommo). Доп.поля и примечания копируются, звонки/чат
сводятся в дайджест-примечание, между сделками ставятся перекрёстные ссылки. Тег
`сборка_из_продажи` защищает новые сделки от антидубля. Код и тесты готовы, фича
выключена флагом `ENABLE_HANDOFF=false` вне авто-раскатки — включение после
smoke-теста на боевом (визуальная проверка ленты в Kommo, RUNBOOK §2в) и
подтверждения владельца.

**DoD этапа 2:**
- Нельзя оставить активную сделку без задачи.
- Превышение времени на этапе видно РОПу и менеджеру.
- Прогрев системно возвращается в работу.
- После оплаты сделка уходит в «Сборку» с контекстом, won корректно проставляется.

## 8. Этап 3 — дашборд (4–5 дней)

**Цель:** руководство видит метрики без ручных выгрузок; данные автоматически тянутся из Kommo. **Базовый минимум сначала** (чётко и твёрдо, без лишнего), расширение разделов — потом.

### 8.1 Две вкладки с переключателем РОП ↔ Маркетинг
Один доступ, кнопка переключения меняет набор метрик (разграничение прав — по желанию клиента, пока не требуется).

**Вкладка РОП:**
- Скорость ответа менеджера на новый лид (в Kommo нативно не реализовано — выгружаем сами).
- Приход лидов, открытые сделки по этапам и по менеджерам.
- Конверсия по этапам (переход этап→этап) — видеть, где теряют клиентов и над каким этапом работать с персоналом.
- Просроченные задачи по менеджерам, сделки без движения / дольше SLA.
- Won/lost, общая конверсия.

**Вкладка Маркетинг (сквозная аналитика):**
- Кол-во qual-/non-qual-лидов.
- Привязка к рекламной кампании: какая кампания → лид → продажа или отказ.
- Источники/каналы и их результативность.

Конкретный список метрик клиент пришлёт; верхний фильтр по периоду — на обеих вкладках.

### 8.2 Реализация
- Данные тянутся из Kommo API на сервер/внешний дашборд, обновление по расписанию (ориентир — каждые 10 минут).
- Сначала прототип вида на моковых данных → утверждение → подключение реальных данных. Прототип уже показан клиенту.

**DoD этапа 3:**
- Дашборд: 2 вкладки (РОП/Маркетинг) с согласованным минимумом метрик, автообновление.
- РОП видит скорость ответа, конверсию по этапам, просрочки и застой; маркетинг — сквозную аналитику по кампаниям.

## 11. Критерии приёмки проекта

- Менеджеры стабильно общаются в WhatsApp/Telegram (белая интеграция), отправка КП/файлов не зависит от телефона Павла.

- У активных сделок есть следующий шаг; этапы контролируются по времени, застой подсвечивается уведомлением в Telegram.
- Won → Сборка работает с сохранением истории.
- Дашборд: 2 вкладки (РОП/Маркетинг) с автообновлением из Kommo.
