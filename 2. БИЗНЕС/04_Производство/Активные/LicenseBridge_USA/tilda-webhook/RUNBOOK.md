# RUNBOOK — LicenseBridge Hub

Операционная инструкция: запуск, наблюдение, разбор очереди ручной склейки, откат.

## 0. Предпусковой чек-лист (freeze-audit)

1. **Backup** текущего сервиса на VPS: `/opt/licensebridge-tilda-webhook`, `.env` (chmod 600),
   Compose, образ. Снимок Kommo уже снят: `backups/kommo_pre_nova_2026-07-24_174351/`.
2. **Preflight** — сверить ID с реальным аккаунтом:
   ```bash
   docker compose run --rm worker python -m app.preflight
   ```
   Ожидаемо `preflight OK`. Ошибки (неверный pipeline/status/owner/field) — исправить `.env`.
   Вне shadow неверная конфигурация **не даст** запуститься mutation-worker.
   Сверка 2026-07-24 по боевому аккаунту пройдена: Pipeline `11274779`, «Новая заявка»
   `108112044`, Сборка `12079591`, Александра `15648532`, Полина `15293564`, Phone `142532`
   (до 19.08.2026 дефолтным ответственным была Илона `15537380`, уволена).
3. **Зафиксировать чужие вебхуки/каналы** Kommo, создающие сделки в обход hub:
   Teletype (`delete_lead`, `status_lead`), Wazzup24 (полный набор), Make — отключён.
   Наш вебхук добавляется отдельно и их не ломает.
4. **NOVA** отключена полностью (2026-07-24) — гонок с её чисткой больше нет.

## 1. Регистрация в Kommo (разово)

**Отдельная интеграция не нужна.** Подписка на вебхуки создаётся тем же долгосрочным
токеном существующей частной интеграции (scope `crm`); Redirect URI нужен только для

```bash
python3 scripts/register_kommo_webhook.py --list   # посмотреть текущие
python3 scripts/register_kommo_webhook.py          # подписать наш URL
```

События: `add_lead`, `status_lead`, `add_contact`, `update_contact` →
`https://72-56-123-137.sslip.io/kommo/webhook/<KOMMO_WEBHOOK_SECRET>`.
Tilda/Pleep уже шлют на `/tilda/webhook` и `/pleep/sync` — без изменений.

## 2а. Репетиция на боевой базе (замена суточной выдержки)

Выдержка этапа ловит ошибки только на живом трафике, а его мало (несколько заявок в
сутки). Репетиция даёт ту же проверку за минуты: сканер находит **все** группы дублей
по телефону и прогоняет их через обычный конвейер. В shadow это «что сделал бы», на
боевом этапе — реальная разборка базы.

```bash
cd tilda-webhook
ssh licensebridge-hub "cd /opt/licensebridge-tilda-webhook && \
    docker compose exec -T worker python - sweep" < scripts/rehearsal.py
# подождать 2-3 минуты (37 групп ≈ 4 мин при лимите 6 rps)
ssh licensebridge-hub "cd /opt/licensebridge-tilda-webhook && \
    docker compose exec -T worker python - report" < scripts/rehearsal.py
```

Отчёт показывает разбивку по вердиктам и номера групп, оставшихся **без решения** —
это и есть индикатор дефекта. Прогон 2026-07-24 на 1830 контактах вскрыл четыре
ошибки, которые сутки наблюдения не показали бы:

| Что нашли | Симптом | Исправлено |
|---|---|---|
| Поиск по телефону не видел половину дублей | номер лежит и как `7473361387`, и как `+1747…`; Kommo матчит подстроку цифр | `identity.phone_query_variants` — сначала национальные 10 цифр |
| «Autocontact +1» склеивались в одну группу | в поле телефона один код страны | `normalize_phone` отбрасывает короче 8 цифр |
| Дубль на втором номере карточки не находился | проверялся только первый телефон | `worker._resolve_contact` перебирает все номера |
| Комментарии менеджеров терялись при склейке | карточку дубля потом удаляют руками | `dedup_contacts._carry_notes` |

## 2в. Handoff Pipeline → Сборка (won создаёт сделку производства)

Отдельная от авто-раскатки фича (`ENABLE_HANDOFF`) — меняет бизнес-процесс
(won больше не «зависает» в Pipeline ради истории), поэтому включается только
руками, после подтверждения владельца и smoke-теста на боевом. Механизм и
guard'ы — `tilda-webhook/app/handoff.py`, план — `.cursor/plans/handoff_pipeline_to_sborka_*`.

**Статус: включено на боевом 13.08.2026.** С 24.07 по 13.08 код был задеплоен, а
ключа `ENABLE_HANDOFF` в боевом `.env` не было вовсе — значение бралось из
дефолта `false`, и каждый won уходил в `handoff.shadow` без создания сделки.
Поймали на сделке `27530563`. Отсюда правило: **после любого деплоя сверять
боевой `.env` с `.env.example`** — новые ключи туда не приезжают сами.

**Перед включением — обязательный smoke-тест на одной реальной сделке:**

1. Деплой кода (без включения флага, `ENABLE_HANDOFF=false`): убедиться, что
   preflight и тесты проходят, `docker compose exec worker python -m app.preflight`.
2. Прогон в shadow — взять `lead_id` реально выигранной сделки Pipeline и позвать
   ручной эндпоинт:
   ```bash
   K=<INTERNAL_API_KEY>; H=https://72-56-123-137.sslip.io
   curl -s -X POST $H/internal/handoff -H "X-Internal-Key: $K" \
        -H 'Content-Type: application/json' -d '{"lead_id": 123456}'
   ```
   Ожидаемо `{"ok": true, "action": "handoff.would_create", ...}` — ничего не создалось,
   только `log_decision`.
3. Включить `ENABLE_HANDOFF=true` в `.env`, передеплоить, повторить тот же вызов на
   **той же или другой** выигранной сделке (эндпоинт идемпотентен по `lead_id`, поэтому
   для реального создания нужна сделка, ещё не имеющая записи в `handoffs`).
   Ожидаемо `{"ok": true, "action": "handoff.created", "assembly_lead": <id>, ...}`.
4. **Проверить глазами в Kommo UI** карточку `assembly_lead` в «Сборке»:
   - в ленте видны прежние WhatsApp/Telegram-сообщения и звонки контакта
     (не только «см. в контакте» — событие должно быть внутри ленты самой сделки);
   - из этой карточки можно ответить клиенту, и ответ уходит в тот же канал;
   - доп.поля и бюджет на месте, есть перекрёстные примечания «Продажа: сделка #…» /
     «Сборка: сделка #…», на новой сделке тег `сборка_из_продажи`.
5. Если пункт 4 (видимость чатов) не подтвердился — не включать фичу для всех:
   разобраться отдельно (расширенный `HANDOFF_COPY_NOTES`-дайджест уже включён по
   умолчанию как частичная компенсация; следующий шаг — сравнить с виджетом F5
   «Копирование сделок», см. план).
6. Тестовую сделку из Сборки удалить руками через UI (`DELETE /leads/{id}` → 405,
   API не умеет) — по фильтру тега `сборка_из_продажи` + номеру.

**Откат / что делать с ошибочной сделкой:**
- Мгновенно выключить: `ENABLE_HANDOFF=false` в `.env` → `docker compose up -d`
  (новые won перестают плодить сделки в Сборке, уже созданные остаются).
- Ошибочно созданная сборочная сделка: снять с неё тег `сборка_из_продажи`, чтобы не
  путать с легитимными, и разобраться руками (объединить/удалить в UI). Запись в
  таблице `handoffs` руками не трогать — она только для идемпотентности.
- Проверка накопленного: `SELECT * FROM handoffs ORDER BY id DESC LIMIT 20;`

**Пропущенные won (если флаг был выключен или сервис лежал):** `scripts/handoff_backfill.py`
находит выигранные сделки Pipeline без пары в «Сборке» и прогоняет их через тот же
`run_handoff`. Сделки, у контакта которых сделка в «Сборке» уже есть (менеджер завёл
руками), пропускаются — иначе получим дубль, который антидубль не ловит.

```bash
ssh licensebridge-hub "cd /opt/licensebridge-tilda-webhook && \
    docker compose exec -T worker python - list 2026-07-24" < scripts/handoff_backfill.py
# тот же вызов с `apply` вместо `list` — применить
```

**Регламент для Илоны и Полины (после включения):** сделку между воронками не
перетаскивать руками — при переводе Pipeline-сделки в статус «Успешно реализовано»
хаб сам заведёт сделку в «Сборке» на этапе «Заполняют анкету» с контактом и
историей; ручной перенос создаст дубль (система его не считает дублем — тег
`сборка_из_продажи` — и не сможет отличить ручной перенос от легитимного повтора).

## 3. Авто-раскатка: решения принимает сервер

`AUTO_ROLLOUT=true` (по умолчанию). Worker сам двигается по лестнице этапов, если
выдержано время **и** нет признаков сбоя. Вручную ничего включать не нужно.

| Этап | Что включается | Выдержка до следующего |
|---|---|---|
| 0 `shadow` | ничего не меняем в Kommo, только считаем решения (лиды Tilda/Pleep создаются) | 24 ч и ≥20 решений |
| 1 `assignment` | распределение новых лидов (дефолтный ответственный / наследование) | 24 ч |
| 2 `deals` | дубль-сделки: перенос примечаний + «Провал» с причиной «дубль», свёртка Pipeline→Сборка | 24 ч |
| 3 `contacts_no_chat` | soft-merge контактов без переписки | 24 ч |
| 4 `contacts_light` | merge контактов с лёгким читаемым чатом (финал) | — |

**Стоп-условия продвижения** (этап замирает, назад не откатывается сам):
любое событие в `deadletter`, очередь `pending` > 100, отказ preflight.

Наблюдение — страница статуса (открыть в браузере):

```
https://72-56-123-137.sslip.io/status?key=<INTERNAL_API_KEY>
```

Ручное управление без деплоя:

```bash
K=<INTERNAL_API_KEY>; H=https://72-56-123-137.sslip.io
curl -s -X POST $H/internal/rollout -H "X-Internal-Key: $K" \
     -H 'Content-Type: application/json' -d '{"action":"pause"}'            # заморозить этап
curl -s -X POST $H/internal/rollout -H "X-Internal-Key: $K" \
     -H 'Content-Type: application/json' -d '{"action":"resume"}'
curl -s -X POST $H/internal/rollout -H "X-Internal-Key: $K" \
     -H 'Content-Type: application/json' -d '{"action":"set_stage","stage":0}'  # назад в shadow
```

Проверка решений в БД (если нужно глубже страницы статуса):

```sql
SELECT action, count(*) FROM decisions WHERE shadow GROUP BY action ORDER BY 2 DESC;
SELECT * FROM decisions ORDER BY id DESC LIMIT 50;
```

Ручной режим (если авто-раскатку выключили): `AUTO_ROLLOUT=false` + флаги
`SHADOW_MODE`/`ENABLE_*` в `.env`, затем `docker compose up -d`.

## 4а. Ограничение Kommo: удалять из API нельзя

`DELETE /api/v4/leads/{id}` и `/contacts/{id}` → **405** (политика платформы, проверено
2026-07-24). Поэтому «устранение дубля» = снять с него работу и пометить:

| Что делает сервер | Что остаётся человеку |
|---|---|
| переносит примечания/звонки в основную сделку, перелинковывает сделки на старший контакт, копирует поля, сообщения и комментарии менеджеров с карточки дубля | — |
| **дубль-СДЕЛКА:** тег `дубль` + этап «Закрыто и не реализовано» с причиной «дубль (есть другая сделка у того же клиента)» (`DUP_LOST_REASON_ID`) | ничего: сделка ушла из рабочих этапов, история сохранена |
| **дубль-КОНТАКТ:** тег **`дубль_удалить`** на пустую карточку (сделки и поля уже переехали) | раз в неделю: фильтр по тегу → выделить всё → удалить |

Главной остаётся сделка, которая **дальше по воронке**; при равных этапах — более
старая. В «Провал» уезжает более свежая заявка с начальных этапов.

**Предохранитель:** если хотя бы одна сделка дубля не переехала (ошибка API), склейка
отменяется — дубль уходит в очередь ручной склейки и тег `дубль_удалить` не ставится.
Иначе карточку удалили бы вместе с непереехавшей сделкой.

Разово разобрать УЖЕ накопившиеся дубли (сухой прогон, затем `--apply`):

```bash
python3 scripts/dups_to_lost.py
python3 scripts/dups_to_lost.py --apply --csv /tmp/dups.csv
```

Проверить объём накопившегося:

```sql
SELECT action, count(*) FROM decisions WHERE action='dup.marked' GROUP BY action;
```

## 4в. Кто может владеть сделкой продаж (19.08.2026)

Признак продавца один: **добавочный в карте телефонии** (`TELEPHONY_EXT_USERS`). Кто
не принимает звонки, тот не получает ни новых лидов, ни задач «перезвонить» —
иначе карточка висит там, где продавец её не видит. Так выпадают Павел (владелец
аккаунта, сделки создаёт его сценарий), уволенные (`DEPARTED_OWNER_IDS`) и
неактивные. Полина в продажах новых лидов не получает, но её **начатые** сделки
за ней остаются: `holds_sales_card()` шире, чем `sells()`.

Раз в час (`OWNER_SWEEP_INTERVAL_SEC=3600`) воркер подметает воронку продаж и
возвращает дежурному продавцу карточки, осевшие на том, кого в команде нет.
Событие создания такие не ловит: сделку мог завести сторонний сценарий или
перенести человек руками.

**Грабли Kommo:** `filter[pipeline_id]` в `/leads` сервер может проигнорировать и
вернуть все воронки. 19.08 из-за этого подметание сняло с Полины 44 карточки
«Сборки», их вернули по журналу `entity_responsible_changed`. Воронку теперь
проверяет сам код, а не только фильтр. Любой массовый обход `/leads` писать так же.

Разово перенести карточки уволенного:

```bash
python3 scripts/reassign_owner.py --from <id> --to <id>          # сухой прогон
python3 scripts/reassign_owner.py --from <id> --to <id> --apply   # снимок для откатa в scripts/snapshots/
```

## 4б. Переписка мессенджеров: где она и почему её «не видно» (19.08.2026)

Жалоба «в Kommo нет истории переписки, непонятно, что отвечает бот» разобрана. По
живому аккаунту за август: **291 входящее и 968 исходящих** сообщений, канал
Wazzup рабочий (261 входящее в WhatsApp), привязка к карточкам верная — на 40
проверенных сделках чат сидит на контакте самой сделки. То есть история не
теряется, теряется её видимость.

Три ограничения Kommo, из которых всё следует:

| Ограничение | Проверено |
|---|---|
| сообщения не попадают в примечания: `amomessage` в аккаунте **0** | 24.07, повторно 19.08 |
| `GET /leads/{id}?with=talks` на сделке отдаёт пусто | 19.08, сделка 29892373 |
| `GET /events?filter[entity]=lead&filter[entity_id]=<сделка>` чат-события **не возвращает вовсе** | 19.08: по карточке 31 событие и ни одного чат-события, при 21 сообщении клиента |
| текстов сообщений API v4 не отдаёт — только факт, канал, автор, время | 19.08 |

Читать переписку можно **только общим потоком** `GET /events?filter[type]=…`, а
затем группировать по сделке — это и делает `app/chat_events.py` (окно кешируется,
иначе каждый дедуп тянул бы тысячи событий).

Из-за первых двух пунктов наш прежний детектор `_lead_has_chat` (notes + talks)
всегда отвечал «переписки нет», и подсказка «на дубле была переписка» не попала в
живую карточку ни разу. Отсюда и жалоба: за август **41 сделка** с перепиской
оказалась дублём или в «Провале», на них осталось **98 сообщений клиентов**, а у
28 дублей из 41 в примечании не было даже ссылки на рабочую сделку.

Что теперь делает сервер: при устранении дубля в живую карточку пишется адрес
переписки и цифры («клиент 21, исходящих 15, из них ботом 13, последнее 18.08»), а
в дубль — ссылка на рабочую сделку. Перенести сами сообщения нельзя, поэтому в
карточке лежит указатель, а не копия.

Разово прошить то, что уже накопилось (пишет только там, где говорил клиент):

```bash
ssh licensebridge-hub "cd /opt/licensebridge-tilda-webhook && \
    docker compose exec -T worker python - list 2026-08-01" < scripts/chat_digest_backfill.py
ssh licensebridge-hub "cd /opt/licensebridge-tilda-webhook && \
    docker compose exec -T worker python - apply 2026-08-01" < scripts/chat_digest_backfill.py
```

Скрипт отдельно печатает сделки, где переписка есть, а живой карточки у клиента
нет вообще: за август таких 10, включая клиента с 22 сообщениями. Это не техника,
а решение менеджера — карточка закрыта, писать некуда.

Чего техника не покажет: **текст** сообщений бота. Он либо в панели Wazzup, либо в
редакторе Salesbot в Kommo. Доступ в кабинет WhatsApp запрошен у Павла 19.08.

## 5. Разбор очереди ручной склейки (менеджер)

Спорные пары помечены маркером + тегом пары из пула. Менеджер:

1. Фильтр в Kommo по тегу `need_merge_contact` (или `need_merge_deal`) — вся очередь.
2. Внутри группы — общий тег пары `mc_NN` / `md_NN` → показывает ровно кого с кем клеить.
3. Списки → Объединить (native-merge Kommo, история/чаты сохраняются). **Теги снимать не нужно.**
4. Сервер сам вернёт освободившийся тег в пул (еженедельный job `reclaim`).

Состояние очереди/пула:
```sql
SELECT reason, count(*) FROM dup_manual WHERE status='open' GROUP BY reason;
SELECT kind, status, count(*) FROM merge_slots GROUP BY kind, status;
```

### 6в. Что делать по каждому алерту

Первое действие важнее диагноза: чем меньше думать в момент алерта, тем быстрее
реакция. Каждая строка ниже — реальный инцидент, а не гипотеза.

| Пришло | Первое действие | Чем это было раньше |
|---|---|---|
| добавочный не зарегистрирован | позвонить менеджеру: запущен ли MicroSIP, не в VPN ли он | 102 лежал 07–13.08, узнали от клиента |
| транк или регистрация Telnyx лежит | `pjsip show registrations`, при `none` — `pjsip send register telnyx_reg`; параллельно проверить, не кончился ли баланс Telnyx | входящие и исходящие встают полностью |
| `deadletter` | `SELECT id, last_error FROM inbox WHERE status='deadletter'`; починить причину, вернуть `status='pending', attempts=0` | карточка, которой для менеджера просто нет |
| тишина у менеджера в рабочие часы | сначала проверить регистрацию добавочного, только потом спрашивать человека | тот же отвал софтфона, вид с другой стороны |
| всплеск заявок | открыть сценарий Make Meta → Kommo и историю запусков | 11.08 сценарий налил дублей заявок |
| сводка не пришла к обеду | `docker compose ps` на хабе, `curl /health` | до сводки такой проверки не было вовсе |
| в сводке больше половины соединений короче 10 с | прослушать 5 записей: спам-метка или голосовая почта | ровно то, что дало «34 лида без контакта» |
| напоминание про spam-статус | открыть кабинеты Hiya и Free Caller Registry, сверить флаг по каждому DID | метка вернулась бы незаметно |
| клиент написал, человек не ответил | открыть карточку по ссылке из алерта и ответить; ответ бота ответом не считается | в июле так осталось без ответа 63,6% чатов, медиана ответа 8 ч |

Правило на будущее: если о поломке снова сообщил клиент, а не алерт, значит
нехватает проверки. Добавлять её в `app/monitor.py` тем же вечером, пока помним
симптом, — это дешевле любого разбора потом.

Токен только в `.env` хаба: наблюдатель на Asterisk отдаёт текст в
`POST /internal/alert` (ключ `LB_KEY` из `/etc/asterisk/lb-hub.env`), а хаб
пересылает. Проверка живой цепочки:

```bash
curl -s --data-urlencode "key=$INTERNAL_API_KEY" \
     --data-urlencode 'text=проверка алертов' \
     https://72-56-123-137.sslip.io/internal/alert   # sent | skipped
```

`skipped` — токен не задан или это повтор в окне молчания. Восстановление
добавочного и транка тоже приходит сообщением: молчание после алерта нельзя
читать как «починилось».

### Линия на одну смену — снято 31.08.2026

Павел (добавочный 101) раньше садился на линию 1 с 16:00 до 21:00 по Калифорнии.
Схема ниже — как это работало, не текущий режим.

1. `.env`: `TELEPHONY_EXT_USERS` += `101:13291175` (без этого его звонки в Kommo
   без автора), `TELEPHONY_SALES_ORDER=103,101`, `TELEPHONY_DID_EXT=1:101,3:103`.
   Владелец линии учитывается только если он есть в `SALES_ORDER` — см.
   `ring_order()`.
2. **`docker compose restart` новый `.env` не читает** — контейнер поднимается со
   старым окружением, и роут молча отдаёт прежний порядок. Только
   `docker compose up -d --force-recreate api worker`.
3. Границы смены держит **постоянный таймер**, а не одноразовые. Смены не
   перекрываются (Александра 09:30–15:00, Павел 16:00–21:00 по LA), поэтому хватает
   двух состояний: `/usr/local/bin/lb-line1-owner.sh pavel|sasha`.

```bash
# кто должен владеть линией по часам Калифорнии — считает сам скрипт
lb-line1-auto.timer → /usr/local/bin/lb-line1-auto.sh   # каждые 10 минут, idempotent
systemctl list-timers "lb-line1*" --all      # проверить, что таймер жив
/usr/local/bin/lb-line1-auto.sh              # применить расписание прямо сейчас
/usr/local/bin/lb-line1-owner.sh pavel       # взять линию вне расписания (до 10 минут)
```

Переключение пишется в `/var/log/lb-line1-owner.log`.

**Почему не одноразовые таймеры (урок 25–31.08.2026).** 25.08 в 04:00 таймер вернул
линию Александре, новых никто не поставил — и неделю звонки в смену Павла уходили
на Александру, один клиент так и потерялся. Плюс деплой хаба перезаписывает `.env`
целиком: 28.08 он затёр из карты добавочных `101:13291175`, и роут перестал знать
Павла вовсе. Периодический idempotent-прогон закрывает оба случая и переход на
зимнее время; строка `101` в `.env.example` теперь постоянная, деплой её не теряет.

Границы смены живут в самом `lb-line1-auto.sh` (`SHIFT_FROM`, `SHIFT_TO`, зона
Калифорнии). Меняются часы работы — правится скрипт, `.env` руками не трогаем.

Роут — половина дела: **софтфон 101 должен быть зарегистрирован**. По журналу
Asterisk 101 не регистрировался ни разу (только ошибки «Endpoint '101': Could not
create dialog to invalid URI»), значит MicroSIP на его стороне не подключён и
звонок до него не дойдёт при любом расписании. Проверка:
`asterisk -rx "pjsip show contacts"` — в смену Павла там обязан быть контакт 101.

4. Проверка после каждой правки — роутом, а не глазами по `.env`:
   `curl -s -X POST -d "key=$K&phone=15551234567&did=1" .../internal/call/route`
   → `101-103`, для `did=3` → `103-101`.

Чего эта схема **не** делает: клиент, закреплённый за Александрой, звонит ей
первой даже на линию 1 — ответственный в `ring_order()` идёт раньше владельца
линии. Владельцу первым достаются ничьи и новые номера.

Выключить телефонию, не трогая остальной хаб: `ENABLE_TELEPHONY=false` в `.env`
+ `docker compose up -d`. Роуты продолжат отвечать (звонки не сорвутся), но в
Kommo ничего писаться не будет.

Частое:
- в карточке нет звонка → смотреть `grep lb-call /var/log/syslog` на Asterisk:
  дошёл ли отчёт, и `docker compose logs worker | grep call.` на хабе;
- плеер молчит → `curl -I` по ссылке из примечания; 404 = файла нет на Asterisk,
  502 = хаб не достучался до `:8088` (проверить правило ufw для 72.56.123.137).

## 8б. Лид-машина: WhatsApp → AI-звонок Pleep → SMS (с 10.08.2026)

Отдельный флаг `ENABLE_LEADFLOW`, вне авто-раскатки. Схема, ТЗ на ботов и порядок

| Роут | Кто зовёт | Что делает |
|---|---|---|
| `POST /internal/leadflow/ai-call` | Salesbot WhatsApp по таймауту | звонок агенту сейчас или после тихих часов клиента |
| `POST /internal/pleep/outcome` | HTTP-tool в сценарии Pleep | этап/задача/SMS/тег по итогу разговора |

Наблюдение:

```sql
SELECT lead_id, phone, tz, status, attempts, scheduled_at, outcome
FROM ai_calls ORDER BY id DESC LIMIT 20;
SELECT action, count(*) FROM decisions
WHERE action LIKE 'ai_call%' OR action LIKE 'pleep%' OR action LIKE 'leadflow%'
GROUP BY action ORDER BY 2 DESC;
```

Частое:

- `ai_call.deferred` и звонок так и не ушёл → worker считает окно каждые
  `AI_CALL_SWEEP_INTERVAL_SEC`; проверить `docker compose logs worker | grep 'ai call'`.
- `ai_call.failed` с «нет связи с AMI» → на Asterisk `asterisk -rx 'manager show users'`
  и правило ufw для 72.56.123.137 на порт 5038.
- итог от Pleep не приходит, но разговор был → в панели агента проверить HTTP-tool
  и ключ `X-Api-Key` (равен `PLEEP_API_KEY`); недозвон хаб закрывает сам по отчёту
  Asterisk, а состоявшийся разговор — только по итогу от Pleep.
- клиенту ушло второе SMS / этап переставился дважды → так быть не должно:
  `ai_calls` уникальна по `lead_id`, смотреть, не создались ли две сделки на контакт.

Выключение: `ENABLE_LEADFLOW=false` → `docker compose up -d` (хаб перестаёт звонить
и трогать этапы). Перевод входящих на агента живёт отдельно, на Asterisk:
`asterisk -rx 'dialplan set global LB_AI_ON 0'`.

пропущенные вебхуки). Точные дубли — отдельным отчётом; спорные — вручную.
