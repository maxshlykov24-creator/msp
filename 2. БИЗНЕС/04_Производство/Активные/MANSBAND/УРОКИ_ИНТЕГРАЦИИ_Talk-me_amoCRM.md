# Уроки: Talk-me ↔ amoCRM Chats (мост), Mansband и повторяемость

Краткая выжимка для следующего агента/клиента. Детали кода — в [`talkme-amojo-bridge/README.md`](../../../../talkme-amojo-bridge/README.md).

---

## Что выбирать заранее

| Решение | Почему |
|--------|--------|
| **Внешняя интеграция** amo (OAuth, серверная логика), не «приватный виджет» в amo | Нужен только backend-мост, без JS в интерфейсе amo. |
| **Свой домен + HTTPS** под вебхуки с первого дня | Бесплатные `*.twc1.net` упираются в **лимит Let's Encrypt на весь зону** — сертификат может не выпустить; свой домен снимает риск. |
| **Webhook канала amo Chats** вида `https://FQDN/amojo/v2/hooks/:scope_id` | Меняется **только через ТП amo** после регистрации канала; в карточке интеграции самому не подставить. |

## Ошибки и как не повторять

1. **Секреты в чат** — не просить и не использовать пароли root/токены в переписке; сразу вести в `_private/*.env`, менять скомпрометированное.
2. **Неполный FQDN** (например только поддомен без зоны) — всегда полное имя хоста для DNS и certbot.
3. **«Приватная интеграция» vs внешняя** — путаница тормозит; для API-чатов amo нужна **внешняя** интеграция + Chats API (`amojo.amocrm.ru`), не путать с marketplace-виджетом.
4. **Подписи amojo** — исходящие: `Date`, `Content-MD5`, `X-Signature` по доке; входящий вебхук v2: `X-Signature` = HMAC-SHA1 **от сырого тела** (в PHP-примере amo тело `trim` — при 401 проверить совпадение с/без trim).
5. **Talk-me вебхук: поле секрета** — в реальном JSON приходит **`secretKey`**, не `secret`; без парсинга мост молча отбрасывает событие (`secret mismatch`), в amo при этом может работать **другая** интеграция.
6. **Структура `newMessageFromClient`** — ключевые поля в `data`: `dialog.id`, `message.id` / текст в `message.content.text`, клиент **`client.clientId`** (не угадывать по старым примерам).
7. **Расхождение кода на сервере и локально** — после правок обязательно **одинаковые** `main.py` + `talkme_client.py` и **пересборка** контейнера; иначе `TypeError: unexpected keyword argument` и amo показывает «пользователь недоступен» / внутренние ошибки.
8. **Исходящее amo → Talk-me** — в `sendToClient` нужны **`client.id`** (Talk-me `clientId` из вебхука, хранить в маппинге диалога), **`operator.login`**, текст; без `clientId` ответ невозможен.
9. **Дубли сделок: чат в Inbox vs примечания** — признак: в payload Talk-me есть **`dataProviderEntities` с platformId `amocrm`**. Значит **параллельно** живёт нативная связка Talk-me↔amo. Отключать в **amo**: Настройки → Интеграции / Источники / при необходимости вебхуки с адресами Talk-me; в ЛК Talk-me «всё отключено» бывает вводит в заблуждение.
10. **Медиа** — у Talk-me в json-doc для оператора по сути **`sendToClient` с текстом**; отдельный «отправить файл клиенту» как у мессенджеров может отсутствовать — реалистичный fallback: **текст + публичная ссылка** на файл из amo; входящие вложения от клиента — парсить `content.attachments[].url` и слать в amo как `picture` / `file` и т.д. по API чатов.
11. **Таймауты вебхуков** — у Talk-me **нет ретраев**; ответ моста должен быть быстрый, тяжёлое — в фоне.
12. **«Санкции» amoCRM на канал из-за `delivery_status=-1`** — после серии ошибок (например когда `talkme_client_ref=NULL` и мост массово отвечал `-1`) amoCRM **частично глушит исходящие из UI**: оператор видит «Внутренняя ошибка сервера», а хук на мост даже не отправляется. В логах nginx — пустота. Лечится: `DELETE /v2/origin/custom/{channel_id}/disconnect` + `POST .../connect` (одного цикла иногда мало — делать 2). Профилактика: на старте интеграции **не отвечать `delivery_status=-1` веером** — лучше отправить в amo системное сообщение об ошибке и `delivery_status=2`. Долгосрочно «санкции» спадают по мере успешных отправок.
13. **«Внутренняя ошибка сервера» = реальная потеря** — если UI amo показал ошибку, сообщение **не дошло** до моста и до клиента. Оператору нужно **повторно отправить** тот же текст; через 2–3 повтора обычно проходит. Не считать это «ложной» ошибкой UI.
14. **Swap на мини-VPS** — на VPS с 1 ГБ RAM обязательно добавить swap 2 ГБ (`fallocate -l 2G /swapfile && mkswap && swapon` + строка в `/etc/fstab`). Без swap панель Timeweb рисует «100% CPU» при поллинге каждые 30 сек, хотя реальный `load avg` 0.0х.

## Мини-чеклист на нового клиента

- [ ] Домен под мост + A на VPS + Let's Encrypt  
- [ ] Канал Chats в amo + секрет + URL вебхука согласован с ТП под `FQDN`  
- [ ] `scope_id` после `connect`, записан в `.env`/БД  
- [ ] В amo **удалены** старые интеграции Talk-me / источники, если нужен только мост  
- [ ] В Talk-me: один вебхук Online-чата на мост, событие «сообщение от клиента», секрет = `TALKME_WEBHOOK_SECRET`  
- [ ] После первого реального хука — сверить поля JSON и парсер; логировать обрезанный payload только временно, без секретов в проде  
- [ ] Сквозной тест: клиент → Inbox; оператор → виджет; при расхождении — логи моста + доставка `delivery_status`

## VPS Mansband (деплой моста)

- **SSH:** в `~/.ssh/config` хост `mansband-bridge` → ключ `~/.ssh/mansband_timeweb_ed25519` (публичный ключ добавлен в `authorized_keys` на сервере).
- **Каталог на сервере:** `/root/talkme-amojo-bridge` (не `/opt/...` — реальный путь через `find …/docker-compose.yml`).
- **Учётка для агента:** `2. БИЗНЕС/…/MANSBAND/_private/vps_access.env` (в git не попадает): `VPS_HOST`, `VPS_BRIDGE_DIR`, пароль в кавычках из‑за `#` в значении.
- **Обновление кода:** `scp …/app/talkme_parse.py …/app/main.py mansband-bridge:/root/talkme-amojo-bridge/app/` затем на сервере `docker compose up -d --build api`; проверка: `curl http://127.0.0.1:19080/health`.
