# Фотографии вариаций в кассе MANSBAND

## Что должен получить продавец

В поиске, подборе в заявку, составе продажи, возврате и перемещении у подтверждённого товара есть миниатюра. Наведение показывает увеличенный кадр. Нажатие открывает его на компьютере и телефоне. Размер, рост, цена, складской остаток и выбор товара продолжают работать по обычным правилам кассы.

Единица обработки — одна пронумерованная группа **внутри конкретного столбца** листа «Фотосессия». У группы может быть несколько кодов МоегоСклада. Разные размеры одного изделия и одной расцветки получают общий снимок.

**У костюма фото показывается на пиджаке и в общей строке комплекта. Карточки костюмных брюк и жилетов остаются без фото**, включая детали смокинга. Совпадение вариации, размера и цвета с пиджаком этого правила не меняет. Самостоятельные брюки или жилет из раздела одежды можно включить со своим подтверждённым кадром.

## Входные файлы и инструменты

- Оригиналы и книга `13-11-2026-Фотосессия.xlsx` лежат в `/Users/max/Library/Mobile Documents/com~apple~CloudDocs/Фотосессия/`. Исходники остаются в iCloud. Данные о размерах, цвете и росте берутся из карточек кассы.
- Правила отбора лежат в [selection.json](../../scripts/catalog_photos/selection.json). Это накопительный список принятых групп. Вручную меняется только он.
- [photos.py](../../scripts/catalog_photos/photos.py) читает объединённые ячейки Excel, находит исходник и карточки, готовит WebP, проверяет итог по всему каталогу и собирает индекс для интерфейса. На Mac используется Python с Pillow, поддержкой WebP и openpyxl.
- Результат сборки находится в `kassa/apps/web/public/catalog-photos/` и `kassa/apps/web/src/data/catalogPhotos.json`. Список правил применяется к составу полного названия карточки. Поля размера и роста определены по структурированным данным при сборке. Вид изделия, вариация, цвет, крой и узор остаются значимыми. Новый размер с тем же форматом получает тот же кадр.
- Сервер отдаёт миниатюру до 144 пикселей по длинной стороне. Кадр до 1080 пикселей запрашивается при просмотре. Обе версии сохраняют пропорции и ориентацию камеры. Имя пары определяется содержимым. Одинаковая пара у нескольких артикулов занимает одно место. В карточках и в PostgreSQL нет копий изображений.

## 1. Получить свежий каталог

Выполняй команды из одного терминала. Файл CSV содержит только справочник товаров. Для другой партии создай новую временную папку той же командой.

```bash
cd '/Users/max/CURSOR/2. БИЗНЕС/04_Производство/Активные/MANSBAND'
PHOTO_PY='/Users/max/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/bin/python3'
PHOTO_SRC='/Users/max/Library/Mobile Documents/com~apple~CloudDocs/Фотосессия'
PHOTO_RUN="$(mktemp -d /tmp/mansband-photos.XXXXXX)"
PHOTO_JOB='scripts/catalog_photos/photos.py'
umask 077
ssh -T -o BatchMode=yes root@72.56.240.103 'cd /opt/mansband-kassa && docker compose exec -T db psql -Xq -v ON_ERROR_STOP=1 -U kassa -d kassa' > "$PHOTO_RUN/catalog.csv" <<'SQL'
COPY (
  SELECT ms_id, ms_type, name, variation, article, category, size, height,
         color, pattern, fit, suit_part, suit_line
  FROM products
  WHERE ms_type IN ('variant', 'product')
  ORDER BY ms_id
) TO STDOUT WITH CSV HEADER;
SQL
"$PHOTO_PY" "$PHOTO_JOB" scan --source "$PHOTO_SRC" --catalog "$PHOTO_RUN/catalog.csv" --report "$PHOTO_RUN/inventory.json"
```

На 19 ноября в папке было 929 ARW, в таблице 952 пронумерованные группы с 1 128 записями артикулов. По именам файлов у 936 групп нашёлся один исходник, у 9 несколько, у 7 ни одного. Ещё 11 файлов находятся вне таблицы. Один и тот же исходник встречается в разных группах. Эти числа описывают наличие файла. Отдельно проверяется его соответствие товару.

## 2. Выбрать следующую партию

1. Открой `inventory.json`. В `groups` найди группу по первой ячейке столбца артикулов, например `Z2`. Посмотри `category`, `number`, `entries`, `sources` и `catalog`. Пропусти ячейки, уже находящиеся в `selection.json`.
2. Начни с небольшого набора групп со статусом `один исходник`. Открой каждый кадр. Сверь вид изделия, цвет и узор с таблицей и кандидатами каталога. Для группы с несколькими артикулами проверь каждый артикул. Соседний номер или такой же номер в другой колонке — отдельная группа.
3. Допиши объект в конец `selection.json`, используя существующую запись как образец. В `source` укажи имя ARW без расширения, в `variations` точные значения поля «Вариация» из кассы, в `models` полные названия сфотографированных видов изделия до скобки. Цвет и узор скопируй из каталога. Пустой узор передаётся пустой строкой. Для костюма включи в `models` только вид пиджака с `suit_part=jacket` и укажи `suit: true` для общей строки комплекта. Брюки и жилет этой вариации в список не добавляй.
4. Сохрани в рабочем отчёте ячейку, исходник, проверенные коды, цвет и решение по каждому спорному случаю. Для повтора из другого столбца сначала проверь, покрыты ли те же карточки принятой группой. Повторную привязку одной карточки скрипт остановит.
5. После каждой партии отмечай обработанные ячейки. При итоговой сверке укажи для каждой группы из свежего `inventory.json` одно из трёх решений. Для опубликованной группы отметь выпуск. Для уже покрытой группы укажи другую ячейку. Для отложенной запиши причину и вопрос клиенту. Отдельно перечисли исходники вне таблицы. Итоговое количество групп сверяй со свежим отчётом `scan`.

**Как разбирать исключения**

| Ситуация | Действие исполнителя |
|---|---|
| У пиджака, брюк и жилета общий код | По полям `suit_part`, `category` и названию проверь, входит ли изделие в костюм. В костюмной группе отбирай только пиджаки. Сборка остановится, если включить в подборку костюмные брюки или жилет, в том числе без флага `suit: true`. Для отдельно снятых брюк из раздела одежды нужен собственный вид изделия и подтверждённый исходник. |
| В имени фотографии дефис, в МоемСкладе косая черта | Используй кандидата из отчёта. В отбор впиши фактический код кассы со всеми разделителями и знаками `+`. |
| Кандидат появился только после замены латинской `m` на кириллическую `м` | Сверь полный код, вид и цвет с карточкой. После документированной сверки добавь `"confirmed_m": true`. При нескольких кандидатах оставь вопрос открытым. |
| Один код встречается в нескольких цветах | Публикуй только подтверждённую расцветку. Пример N2 показывает, как привязать коричневый `YI8863` и оставить другие цвета отдельно. |
| По одной записи Excel у одного вида нашлись разные сочетания цвета, кроя или узора | Отложи группу. При наличии решения клиента впиши источник и содержание решения в `appearance_evidence`. Выбери точный цвет и узор. Для нескольких вариантов кроя у того же цвета и узора укажи допустимые значения, например `"fits": ["slim fit"]`. |
| Более одного исходника, например B2, либо нет файла, например B85 | Зафиксируй ячейку и имена файлов. Когда клиент выберет основной кадр, укажи его точное имя в `source`, а источник решения в `source_evidence`. Для группы с несколькими файлами выбор ограничен её собственными кадрами. Для пустой группы нужен явно подтверждённый файл, который реально есть в папке. |
| Файл вне таблицы, например `501-черный-2.ARW` | Оставь исходник в папке. В таблице для P2 указан кадр `501-черный-1`. Остальные ракурсы ждут самостоятельного решения. |
| Нет соответствия, совпало только начало кода или расходится вид изделия | Запиши ячейку и расхождение, переходи к следующей группе. После решения клиента допустим `confirmed_codes` со структурой `{"запись из Excel":{"variation":"точный код из кассы","evidence":"источник и решение"}}`. Код должен существовать в свежем каталоге. Подстрока или визуально похожий артикул не подтверждают связь. |

## 3. Проверить и записать

```bash
"$PHOTO_PY" "$PHOTO_JOB" build --source "$PHOTO_SRC" --catalog "$PHOTO_RUN/catalog.csv" --report "$PHOTO_RUN/check.json"
```

Это пробная сборка. Открой `check.json`, сверь `cell`, `source`, `variants`, `sizes`, `heights` у каждой добавленной группы. `matched` — итог по уникальным карточкам всей накопительной партии, `assets` — число уникальных пар изображений. При конфликте, повреждённом исходнике, потере старой привязки или расхождении с ожидаемым охватом сначала разберись с указанной ячейкой. Генерируемый индекс вручную не редактируется.

Для **воспроизведения исправленного пилота** укажи 10 групп и 120 карточек. Для следующей партии подставь проверенные итоги всей партии, включая уже принятые группы.

```bash
"$PHOTO_PY" "$PHOTO_JOB" build --source "$PHOTO_SRC" --catalog "$PHOTO_RUN/catalog.csv" \
  --apply --expect-groups 10 --expect-links 120 --report "$PHOTO_RUN/applied.json"
```

Повтори ту же команду с теми же данными. Число пар, байты и содержимое индекса должны совпасть. Публикация индекса происходит после записи изображений. Проверка защиты существующих правил срабатывает до смены индекса.

## 4. Приёмка в интерфейсе

- В разделе «Поиск товара» выбери «Все разделы» и набери `BAZ3070MTTBE`. Проверь размеры 46 и 60 и обе ростовки 176 и 182. Адрес миниатюры у этих карточек должен совпасть. Во вкладке Network при открытии списка запрашивается только `-s.webp`. После наведения или нажатия появляется `-l.webp`.
- В форме «Продажа» найди `YI8863`. Проверь коричневые карточки и соседний цвет. Нажатие по фото открывает просмотр, нажатие на строку выбирает товар. В смешанной группе каждый доступный кадр подписан своим цветом.
- Найди в подборе продажи оба кода B136 и код D2. У пиджаков рядом с названием видна миниатюра. У всех строк брюк и жилетов отсутствует кнопка просмотра. В «Поиске товара» проверь фото в общей строке костюма. Проверь закрытие через Escape, кнопку и касание снаружи. На телефоне изображение целиком помещается по ширине.
- Проверь по одному новому артикулу в каталоге, подборе, составе заявки и перемещении. Для проверки хватает чтения каталога и локального выбора товара без сохранения заявки.
- Критерий сдачи партии — все принятые карточки показывают ожидаемую фотографию, посторонние карточки её не получили, повторный прогон не создал файлов, в каталоге и продаже нет ошибки поиска. По исключениям оставлен список с ячейками и причинами.

## 5. Выкладка и откат

Следующие партии требуют обновления каталога изображений и интерфейса кассы. Исходники ARW, книгу Excel и выгрузку CSV на сервер не копируют. Для проверки на Mac выполни из папки клиента `(cd kassa/apps/web && ./node_modules/.bin/tsc -b && ./node_modules/.bin/vite build)`. Сверь список изменённых файлов с составом своей партии.

Перед согласованным релизом сохрани версию работающего web-образа и исходные файлы на сервере. Перенеси только индекс и новые WebP. Пересобери сервис `web` и подними его с `--no-deps`. Проверь `/api/health`, вход в кассу, получение изображений с рабочей сессией и отказ HTTP 401 при обращении без неё. Первая партия отдельно содержит исправление сортировки в API каталога. Дальнейшие партии фотографий используют уже исправленный поиск.

Собирай следующую версию на текущих исходниках сервера. Перед переключением сравни SHA-256 действующего индекса с последней опубликованной версией. При расхождении сначала сведи обе партии в накопительном списке. Сохрани старые файлы сборки из `/usr/share/nginx/html/assets/` рядом с новыми в выпускаемом образе. Это позволит уже открытой кассе догрузить нужный файл. Пример такой выкладки и проверки контрольных сумм находится в `release.py` указанной выше серверной папки. После запуска проверь HTTP-ответ и открытие миниатюры у старого и нового артикула.

Для отката верни сохранённый web-образ и предыдущий индекс. При откате именно первого релиза верни также предыдущий API-образ и исходный модуль каталога. Сохрани добавленные WebP вместе с материалами партии. База товаров, документы МоегоСклада и история продаж в этой операции не меняются.

После отката проверь в продаже `M03/642MB3 48`. Если восстанавливаешь выпуск с фотографиями, у пиджака должна быть миниатюра, у брюк и жилета строки должны быть без неё. Первоначальный фотоиндекс до исправления связывал снимок со всеми тремя частями.
