# ТЗ: UTM-метки визита с сайта попадают в поля сделки amoCRM для заявок из чата Talk-me

**Кому:** Архитектор (проектирование) → исполнитель по коду моста `talkme-amojo-bridge`
**Срок:** 2026-09-15
**Собрано:** 2026-09-08, Ио, по запросу владельца «с сайта пришёл лид без UTM, хотя метки быть должны»

---

## Контекст

Заявки с сайта Mansband идут по цепочке Talk-me → мост `talkme-amojo-bridge` → amoCRM Chats API (amojo).
Сделку в этом сценарии создаёт сам amoCRM из входящего чата.

Причина отсутствия меток — трёхслойная:

1. **Парсер выбрасывает UTM.** `app/talkme_parse.py`, функция `parse_talkme_profile` достаёт из вебхука
   только `name`, `phone`, `email`, `profile_link`, `client_id`. Всё остальное оседает в сыром
   `conversation_map.talkme_context.last` и дальше не идёт.
2. **Chats API не умеет писать UTM в сделку.** В `app/main.py` payload для `post_new_message` содержит
   `timestamp`, `msgid`, `conversation_id`, `sender`, `message`. Поля под UTM в amojo нет в принципе:
   чтобы метки легли в карточку, нужен отдельный вызов amoCRM API v4 с записью `custom_fields` сделки.
   Поиск по слову `utm` во всём коде моста не даёт ни одного совпадения.
3. **Сделки из моста идут мимо штатных источников меток.** По `02_Знание/ЗНАНИЯ_ИЗ_ЧАТОВ.md`: метки в
   сделки Mansband проставляет Roistat (коллтрекинг), UTM при переходе в мессенджер — YourGood,
   плюс ручное правило от 2026-03-13 «заявка с `yclid` без `utm_source` → источник Яндекс Директ».
   Ни один из этих механизмов не видит беседу, созданную через Chats API нашим мостом.

Дополнительная гипотеза: раньше метки могла ставить нативная связка Talk-me ↔ amoCRM, которую отключили
из-за дублей сделок (урок №9 в `02_Знание/УРОКИ_ИНТЕГРАЦИИ_Talk-me_amoCRM.md`). Проверяется сверкой даты
отключения с датой последней сделки из чата, где UTM были.

## Итоги разведки (2026-09-08, выполнено)

**Шаг 1 закрыт: Talk-me отдаёт метки.** Проверено на боевой БД моста, 190 бесед.

| Что приходит | Путь в payload | Покрытие |
|---|---|---|
| UTM объектом из 6 ключей | `data.client.utm` → `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`, `utm_referrer` | 152 из 190, из них `utm_source` не пустой у 84 |
| **Идентификатор визита Roistat** | `data.client.roistatVisitId` | **178 из 190 (94%)** |
| Реферер | `data.client.referer` | 114 |
| Полный URL входа, включая `yclid` / `ysclid` | `data.client.lastVisit.page.url` | 190, из них с `clid` — 17 |
| Поисковый запрос | `data.client.searchKeyword` | 126 |

**Шаг 2 закрыт: поля в amoCRM уже заведены, создавать ничего не нужно.** Стандартные поля типа
`tracking_data` в `mansband.amocrm.ru`:

| Поле | id | Поле | id |
|---|---|---|---|
| utm_source | 3133877 | utm_term | 3133879 |
| utm_medium | 3133873 | utm_referrer | 3133881 |
| utm_campaign | 3133875 | roistat | 3133883 |
| utm_content | 3133871 | yclid | 3133905 |

**Диагноз подтверждён на живых сделках.** Три реальных лида из чата (04.09 `maps`, 04.09 `ya`,
01.09 `maps`) — Talk-me прислал метки, в сделках amoCRM все восемь полей пустые. По аккаунту в целом
UTM заполнены у 20% последних 750 сделок: механизм работает для форм и коллтрекинга, но не для чата.

**Главный вывод, меняющий приоритет:** `roistatVisitId` приходит в 94% бесед — чаще, чем сами UTM.
Если писать его в поле `roistat` (3133883), Roistat сам свяжет сделку с визитом и подтянет источник,
канал и расходы. Это и есть то, чего ждёт клиент, когда говорит «метки должны быть». Поэтому
`roistat` пишем первым приоритетом, UTM — вторым.

**Побочная находка:** у одного клиента обнаружены две сделки в одной воронке 9601214 (59565879
и 59565761 «Не определен | Яндекс Карты»). Похоже на дубль чат-сделки и сделки от коллтрекинга.
Отдельно проверить после основной работы, в этом ТЗ не решаем.

### Открытый вопрос по реализации

amoCRM создаёт сделку из чата асинхронно, и Chats API не возвращает её id. Найти сделку можно двумя
путями, выбор за исполнителем на этапе проектирования: либо ловить вебхук amoCRM `add_lead` и
сопоставлять по контакту, либо после отправки сообщения искать сделку по телефону клиента через
`GET /api/v4/leads?query=`. Второй путь проще, но требует задержки и защиты от гонки.

## Definition of Done

1. Тестовый переход на сайт Mansband со специально проставленными UTM в ссылке плюс сообщение в чат →
   в amoCRM создана сделка, в её полях лежат ровно те же значения. Скриншот карточки в отчёте.
2. Повторное сообщение того же клиента в ту же беседу не перезаписывает UTM первого касания
   и не создаёт вторую сделку.
3. Сообщение без UTM (прямой заход) не роняет мост: сделка создаётся, поля пустые, в логах нет traceback.
4. Ошибка API v4 (истёкший токен, отсутствующее поле) не блокирует доставку сообщения в amoCRM:
   чат продолжает работать, ошибка уходит только в лог.
5. Код на VPS и в vault идентичен, контейнер пересобран, `curl http://127.0.0.1:19080/health` отдаёт ok
   (урок №7: расхождение локального и серверного кода уже ломало интеграцию).

## Ограничения

- Не включать обратно нативную связку Talk-me ↔ amoCRM: вернутся дубли сделок (урок №9).
- Секреты только в `_private/*.env`, в git не коммитить.
- Вебхук `/webhooks/talkme` обязан отвечать быстро, у Talk-me нет ретраев: дозапись UTM — фоном (урок №11).
- Не отвечать `delivery_status=-1` веером, иначе amoCRM глушит канал amojo (урок №12).
- Прод-сервер: перед деплоем бэкап БД моста.
- Не трогать поля, которые заполняет Roistat, без отдельного согласования с владельцем.
