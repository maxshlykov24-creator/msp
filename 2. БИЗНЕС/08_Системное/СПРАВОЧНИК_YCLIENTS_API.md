# Справочник — YCLIENTS API (маркетплейс-интеграция)

> База знаний MS Product по интеграции с YCLIENTS через партнёрское приложение. Собрано и проверено на практике **2026-08-07** на проекте [Keris Club](../04_Производство/Активные/Keris_Club/) (App `48693`, Company `2125383`). Используй как отправную точку для **любого** следующего проекта с YCLIENTS — не изобретай заново.
>
> Официальные источники: [developers.yclients.com/ru](https://developers.yclients.com/ru/) (REST API reference) · [support.yclients.com](https://support.yclients.com/1--obshie-materialy-po-yclients/) (база знаний по продукту) · [Доступ к API](https://support.yclients.com/67-68-199--dostup-k-api/) · [Webhooks в YCLIENTS](https://support.yclients.com/67-69-993--webhooks-v-yclients/).

## 1. Модель авторизации

Два уровня токенов в одном заголовке:

```
Authorization: Bearer <partner_token>, User <user_token>
Accept: application/vnd.yclients.v2+json
Content-Type: application/json
```

Base URL: `https://api.yclients.com/api/v1`

| Токен | Что это | Где взять |
|---|---|---|
| **Partner Token** | Токен партнёрского аккаунта (разработчика) | Аккаунт разработчика → «Настройки аккаунта» → «Токен партнера» |
| **User Token** | Токен конкретного пользователя, определяет реальные права на данные филиала | Два варианта: (а) «системный пользователь» приложения — см. §2; (б) `POST /auth` с логином/паролем реального пользователя YCLIENTS (см. §4) |
| **Company ID** | ID филиала | В URL админки: `yclients.com/timetable/{company_id}/...` или после подключения приложения к филиалу |
| **Application ID** | ID приложения в маркетплейсе | Аккаунт разработчика → карточка приложения |

## 2. Права системного пользователя (главный источник 403)

Приложение маркетплейса создаёт **системного пользователя** — его `User Token` выдаётся сразу при создании приложения. Права этого пользователя настраиваются **не в аккаунте партнёра**, а в карточке конкретного приложения:

```
Аккаунт разработчика → Мои приложения → [название приложения] → вкладка «Доступ к API»
```

Там — список чекбоксов по разделам (Журнал записи, Форма записи, Настройки, Клиентская база, Финансы, Лояльность, Онлайн-запись, Обзор, Склад, Чаевые). Отметь нужные — минимум **Настройки** (управление сотрудниками/услугами/категориями) и **Форма записи**.

⚠️ **Критично:** права применяются **в момент подключения приложения к филиалу**, а не при простом сохранении чекбоксов. Если филиал уже подключён с ограниченным набором прав, изменение чекбоксов задним числом **не долетает** до уже созданного системного пользователя. Чтобы обновить права на уже подключённом филиале:

1. Отметь нужные чекбоксы в «Доступ к API» → Сохранить.
2. Переподключи приложение к филиалу — открой ссылку установки ещё раз и подтверди подключение:
   ```
   https://yclients.com/e/mp_{APPLICATION_ID}_{идентификатор_приложения}/
   ```
3. Повтори проверку API (`GET /company/{id}/staff`, `/service_categories`) — 403 → 200.

Симптом: `GET /company/{id}` и `/services` работают (200), а `/staff` и `/service_categories` — `403 Недостаточно прав`. Причина — системный пользователь без прав на разделы «Сотрудники»/«Настройки», а не проблема токенов.

## 3. Настройки подключения (webhook) — обязательное поле

Вкладка **«Настройки для разработки»** в карточке приложения. Поле **«Адрес, на который отправлять уведомления»** — обязательно для сохранения ЛЮБЫХ настроек приложения (включая права из §2). Если не заполнено — форма прав выдаёт ошибку вида «не все поля заполнены», хотя визуально ошибка в другой вкладке.

| Поле | Значение (пример Keris) |
|---|---|
| Адрес уведомлений (webhook) | `https://<host>/webhooks/yclients` |
| Callback Url | тот же адрес |
| Registration Redirect Url | `https://<host>/` |
| Галочки iframe / несколько филиалов | выключить, если не нужны |

Наш приёмник вебхуков (`app/sync.py` в `keris-server`) — референс реализации на будущее.

⚠️ **YCLIENTS не передаёт auth-заголовков в вебхуке** (`User-Agent: GuzzleHttp/7`) и **не доставляет ни query, ни path-хвост** адреса уведомлений — проверено на живом приложении `48693`: при сохранении `…/webhooks/yclients?secret=…` или `…/webhooks/yclients/<secret>` события всё равно приходят на голый `POST /webhooks/yclients`. Обязательная проверка секрета на голом пути → стабильный `401`, в интерфейсе YCLIENTS это не видно.

Практический вывод для marketplace-приложения: принимать голый путь без обязательного секрета; защита — непубличный host + валидация payload. Опциональный path-секрет можно оставить «на будущее».

Формат живого события (2026-08-07): два POST на create записи — `resource=record` и `resource=client`, поля `company_id`, `resource_id`, `status` (`create`/`update`/`delete`), `data` (объект записи/клиента).

Что важно при обработке `resource=record` (проверено живьём на `record 1891440180`):

- `data.datetime` — ISO **с offset** (`2026-08-11T19:00:00+03:00`), `data.date` — то же время naive в поясе филиала. Брать одно и приводить к своему поясу, иначе запись уедет на 3 часа.
- `data.seance_length` — длительность в **секундах**.
- Удаление приходит и как `status=delete`, и как `data.deleted=true` — проверять оба.
- Правка записи в журнале приходит как `status=update` с полным объектом (не diff).
- **Собственный push возвращается эхом:** после `POST /records/{company_id}` платформа шлёт вебхук и на записи, созданные тобой по API. Идемпотентность — по своему `record_id` в БД: если запись уже есть и время/мастер не изменились, событие ничего не меняет. Из вебхука **не пушить обратно** — цикл webhook → push → webhook.
- Обратный маппинг «услуга-зеркало → своя услуга» неоднозначен, если в YCLIENTS держишь 3 зеркала на 20 своих позиций: нужно детерминированное правило выбора + пометка менеджеру доуточнить состав и сумму.

Диагностика:

```bash
grep webhooks/yclients /var/log/nginx/access.log | tail
# 91.105.196.102 "POST /webhooks/yclients HTTP/1.1" 401 ... "GuzzleHttp/7"
```

Диагностический приём: создать запись через `POST /records/{company_id}` — YCLIENTS шлёт вебхук и на API-созданные записи, так что проверять входящий канал можно без виджета и без реального клиента.

## 4. Альтернатива системному пользователю — `POST /auth`

Если нужны права **реального** пользователя (владельца/админа филиала), а не ограниченного системного:

```
POST /api/v1/auth
Authorization: Bearer <partner_token>
{"login": "<телефон или email>", "password": "<пароль>"}
```

Возвращает `user_token` этого пользователя со всеми его правами в филиале. При включённой 2FA — придёт код (email/push), нужен повторный запрос с полем `code`. Пароль не хранить дольше, чем нужно для одного запроса.

## 5. Ключевые эндпоинты (проверено на практике)

| Действие | Метод | Path | Заметки |
|---|---|---|---|
| Получить/изменить филиал | `GET`/`PUT` | `/company/{id}/` | ⚠️⚠️ **`PUT` — полная замена, не патч.** Любое поле, которое не передал, **обнуляется** (проверено на живом филиале: не передал `phones` → телефон стёрся). Всегда: `GET` → смерджить изменения в полученный объект → `PUT`. Плюс `title` обязателен в каждом запросе, иначе `422 Не указано название салона`. Разрешённые поля: `title, address, zip, phones, site, description, short_descr, coordinate_lat, coordinate_lon, social, business_type_id`. |
| Установить график работы | `PUT` | `/company/{company_id}/staff/schedule` | Тело: `{"schedules_to_set":[{"staff_id":123,"dates":["2026-08-10","2026-08-11"],"slots":[{"from":"10:00","to":"22:00"}]}]}`, симметрично `schedules_to_delete` (без `slots`). Даты перечисляются списком — сменный график (4/3 и пр.) генерируется на стороне клиента, «шаблонов смен» в API нет. За один запрос спокойно уходит 150+ дат. **Пока график не задан, сотрудник `is_bookable:false`** и онлайн-запись на него не работает, даже при активных привязанных услугах. Есть и устаревшая пара `GET/PUT /schedule/{company_id}/{staff_id}` — не использовать. |
| Список услуг | `GET` | `/company/{id}/services` | — |
| Создать услугу | `POST` | `/services/{company_id}` | Обязательно `staff` (`{id, seance_length}`). `duration` / `seance_length` — **кратны 300 с** (5 мин), иначе `400`. Новая услуга часто приходит с `active:0`. |
| Изменить услугу | `PUT` | `/services/{company_id}/{service_id}` | Поле `active:1` в `PUT` **принимается** (проверено 2026-08-07) — надёжный способ активировать после `POST`. `is_online:1` — видно в онлайн-записи/картах. |
| Удалить услугу | `DELETE` | `/services/{company_id}/{service_id}` | Используется в `yclients_setup.py --cleanup-old-catalog` при переходе на размерные категории (2026-08-07). |
| Категории услуг | `GET`/`POST`/`PUT` | `/service_categories/{company_id}` · `/service_category/{company_id}/{id}` | Именование пути разное для create (`service_categories`, мн.ч.) и get/put (`service_category`, ед.ч.) — легко ошибиться. **Категории — плоский список, без вложенности**: объект не содержит `parent_id`/подкатегорий (проверено 2026-08-07 живым запросом), только `weight` (порядок сортировки). «Подкатегории» эмулируются только отдельными категориями с содержательным названием. |
| Список/создать сотрудника | `GET`/`POST` | `/company/{company_id}/staff` · `/staff/{company_id}` | Ответ создания — `201`. Иногда первый запрос сразу после предыдущего падает `403 Необходимо продлить лицензию в филиале` — транзиентная ошибка/rate-limit, немедленный повтор того же запроса проходит. |
| Изменить/уволить сотрудника | `PUT`/`DELETE` | `/staff/{company_id}/{staff_id}` | Увольнение — `fired:1` через `PUT`, не через `DELETE` (DELETE — устаревший метод). |
| Записи (push с нашей стороны) | `POST`/`PUT`/`DELETE` | `/records/{company_id}` (создание, `201`) · `/record/{company_id}/{record_id}` (чтение/правка/удаление) | ⚠️ `DELETE` отвечает **пустым телом** (не JSON) — парсер должен это переживать. После удаления `GET /record/{id}` **всё ещё возвращает объект** (soft delete), поэтому проверять факт удаления надо по журналу: `GET /records/{company_id}?start_date=&end_date=` (там записи уже нет). Повторный `DELETE` → `404 Не найдено`. |
| Журнал записей за период | `GET` | `/records/{company_id}?start_date=&end_date=` | Единственная надёжная проверка «что реально видно в журнале». |
| Прочитать графики | `GET` | `/company/{company_id}/staff/schedule?start_date=&end_date=&staff_ids[]=` | Возвращает только даты со сменами; `include[]=busy_intervals&include[]=off_day_type` — занятость и типы выходных. Поле `schedule_till` в `/staff` обновляется с задержкой, ориентироваться на него для проверки горизонта нельзя. |

## 6. Прочие практические наблюдения

- Дефолтная заготовка нового филиала: 1 категория «Категория услуг», 1 услуга «Услуга» (`active:1`, привязана к дефолтному сотруднику), 1 сотрудник «Сотрудник 1». Удобно **переименовывать** эти сущности через `PUT`, а не создавать новые + удалять старые — меньше мусора и сохраняются ID.
- SSH-автоматизация payload с кириллицей: избегай инлайн-JSON в `expect`/heredoc (кавычки/кириллица бьют экранирование и `stdin` спавненного процесса не читается через heredoc). Рабочий паттерн: пишем JSON-файл локально → `scp` на сервер → `curl -d @/tmp/файл.json` через интерактивную SSH-сессию (`expect ... send "команда\r" ...`).
- Всегда перепроверяй результат `PUT` отдельным `GET`. API возвращает `200 success:true` и на запросах, которые не дали ожидаемого эффекта.
- Телефон филиала (`phones`) **записывается** — рабочий формат: массив с человекочитаемой строкой, `["+7 993 368-98-71"]`. Ранние неудачи с `79...`/`+79...` без пробелов — скорее всего формат, а не запрет на запись.
- Координаты (`coordinate_lat/lon`) пишутся обычными float (`55.808457`, `37.024289`); в свежем филиале по умолчанию `0`/`0` — без них пин на Яндекс/2ГИС будет неточным.
- **Диапазон цены (`price_min` ≠ `price_max`) не даёт клиенту выбрать вес/размер питомца** — виджет и карты просто показывают вилку, фактическая цена записи остаётся на догадку менеджера. Рабочее решение (2026-08-07): `price_min = price_max` (точная цена) на **свою услугу под каждый размер**, размеры сгруппированы отдельными категориями (см. `Keris_Club/06_Доступы/ДОСТУПЫ.md`). Побочный эффект в плюс: по `id` выбранной клиентом услуги в вебхуке `record` однозначно узнаётся размер питомца — не нужно гадать/спрашивать заново.

## 7. Открытые вопросы / не решено на 2026-08-07

- Не проверяли на практике `schedules_to_delete` (снятие смен) и точечное изменение уже проставленного графика — только массовую установку.
- Дефолтный «Сотрудник 1» в заготовке филиала: не нашли способа корректно скрыть его из онлайн-записи по API, кроме `fired:1` через `PUT /staff/...`. Пока просто держим его без услуг и без графика (`is_bookable:false`), из виджета он не виден.
