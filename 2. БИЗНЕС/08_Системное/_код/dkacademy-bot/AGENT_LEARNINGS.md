# Handoff: сервис-посредник LiveInform → amoCRM + Telegram

Только то, что повторяется у разных клиентов. Поведение бота и формулировки — в коде/README, сюда не тащим.

## Архитектура

- Прямая интеграция **LiveInform ↔ amoCRM** отключаем: весь поток через сервис (webhook → `track` → запись в CRM + уведомление в TG).
- Уведомления в TG от **изменения поля в amo** не нужны, если статус в CRM заполняет **только** этот сервис и менеджеры поле не правят руками — источник правды: **webhook провайдера доставки**.

## Сеть и Telegram Bot API

- С части хостингов в РФ **исходящий HTTPS к `api.telegram.org` недоступен** (не «баг DNS»). Проверка с сервера: `curl -I https://api.telegram.org`. Обход: **VPS вне РФ** или иной выход в интернет, где запрос проходит.
- Ошибка **`Conflict: webhook is active`**: тот же токен уже на webhook (часто **канал Telegram в amoCRM**). Приложение на **long polling** — снять webhook (`deleteWebhook`), тот же бот **не** вешать вторым каналом на amo.

## amoCRM

- **Сабдомен API** брать из кабинета (`https://…​.amocrm.ru`), не угадывать по названию компании → иначе 401/пустые ответы.
- Поиск сделки по значению **кастомного текстового поля** через **`filter[custom_fields_values][…]`** может давать **400** — рабочий вариант: **`?query=`** по строке трека + проверка, что совпало нужное поле.
- **Несколько контактов / несколько телефонов** на карточке: для доставки TG-уведомления нельзя опираться на один номер из привязки — собирать телефоны **всех** контактов сделки (+ телефон из коллбэка провайдера), искать привязки по любому и по `amo_contact_id`.
- **Код OAuth одноразовый** — пересланный из чата не оживить; для MVP часто достаточно **долгосрочного токена** в `.env`.
- **`redirect_uri` «не найден»**: amo проверяет **резолв/достижимость** URL — нужны **DNS на IP** сервиса и **HTTPS** (или хотя бы корректный резолв по их правилам).

## LiveInform (аналогичные провайдеры)

- В ЛК callback часто задаётся **только URL** — секрет в **пути** (`…/webhooks/…/{token}`) + сравнение через **`hmac.compare_digest`**.
- Тело может быть **`application/x-www-form-urlencoded`**, JSON внутри поля **`data=`** — не парсить сырой body как JSON.
- В коллбэке **`order_id`** иногда = **внутренний id сервиса**, не заказ клиента — явно различать с **`liveinform_id`** (или эквивалентом).
- **Код доставки ≠ поле `status` в callback:** в callback `status` = индексация, доставка в **`track_status`**; в ответе track/v2 доставка в `status`. Классификатор: `track_status` если есть, иначе `status`.
- **Уведомления в TG только по whitelist** смысловых id (`delivery_semantics.py` + шаблоны в `delivery_notify_templates.py`). Вне whitelist — тишина. Дедуп: `li_tg:{track}:{semantic_id}`.
- **Серый статус (нераспознан):** не код `3`/`4` и не матч алиаса → клиенту тишина + алерт в ops-бот (`OPS_ALERT_BOT_TOKEN` + `OPS_ALERT_CHAT_ID`). Дедуп алертов: `li_ops:{track}:{hash}`.
- **204 / «нет средств»** при `track` — типично для несуществующего id или нулевого баланса; отличать от багов в коде.
- Дедупликация вебхуков (таблица обработанных событий) — чтобы повторы не дублировали эффекты.

## Docker / деплой

- Если приложение **вшито в образ** (`COPY`), после правки кода на сервере: **`docker compose up -d --build api`**, а не только `restart`, если нет bind-mount исходников.
- Reverse proxy на хосте → порт приложения из **`docker-compose.yml`** (в этом репозитории пример: `127.0.0.1:19082`).

## Безопасность

- Секреты из чата = **ротация** токенов бота, amo, вебхуков.
- При утечке **пароля SSH**: смена, **ключи**, проверка **drop-in файлов sshd** (cloud-init может вернуть `PasswordAuthentication yes`).

## Сеть VPS Timeweb RU (инцидент 2026-06)

- **Субдомен amoCRM = `dkdkacademy`** (не `dkacademy`!). `AMO_SUBDOMAIN=dkdkacademy`, иначе все запросы → **401**. Долгосрочный токен переиспользуется из аналитики (`/root/dkacademy-analytics/.env` → `AMO_ACCESS_TOKEN`).
- **`api.telegram.org` частично заблокирован**: основной IP `149.154.166.110` — таймаут; рабочий DC по IPv4 — `149.154.167.220`. В `docker-compose.yml` для `api`: `extra_hosts: ["api.telegram.org:149.154.167.220"]`. Проверка: `getMe` через `--resolve` к этому IP = `ok:true`.
- **pip build падает «Network is unreachable»**: `files.pythonhosted.org`/`pypi.org` резолвятся в **IPv6**, IPv6-маршрута нет. Фикс — `build.extra_hosts` с IPv4 Fastly `151.101.0.223`.
- Внутри контейнеров вообще **предпочитается IPv6** при наличии AAAA → если у внешнего хоста есть AAAA и нет IPv4-маршрута, будет «Network unreachable». amoCRM/MAX/LiveInform отдают IPv4 и работают; Telegram — нет (см. выше).
- **rsync по SSH на этот VPS нестабилен** (обрывы/таймауты на передаче данных), хотя короткие `ssh '...'` команды проходят. Надёжный способ залить файл: `ssh ... 'cat > /path' < localfile`.

## Повторное касание — запуск (важно!)

- `REPEAT_TOUCH_ENABLED=true` → воркер прогоняется **сразу на старте** по всему окну `REPEAT_TOUCH_LOOKBACK_DAYS` (60д) и **создаёт сделки** на этапе «Требует касания» (путь сделки **не требует** привязки клиента к боту). Перед боевым запуском всегда сначала **DRY_RUN**; иначе при первом старте создастся бэклог сделок.
- Этап «Требует касания» (воронка «Повторные продажи»): **`status_id=86621210`**, `pipeline_id=10697570`. Успех в «Продажи»: `status_id=142`, `pipeline_id=10694702`.
- Скрипт `scripts/backfill_*` **не лежит в образе** (`COPY app` только) → запускать логику инлайном: `docker compose exec -T api python3 -c "from app.repeat_worker import process_repeat_touch; ..."`.

## Маршрутизация без поддомена

- Вебхук/OAuth бота повешены на существующий домен аналитики **по путям**: в vhost `dkacademy-analytics.ru` добавлены `location /webhooks/liveinform` и `location /oauth/callback` → `proxy_pass http://127.0.0.1:19082`; остальное (`/`) → аналитика `:19090`. HTTPS-сертификат общий.

## Персистентность привязок — клиенты НЕ должны повторять /start

- Привязки (`contact_binding`) живут в **именованном томе** `dkacademy_bot_pg`. `docker compose up -d --build` пересоздаёт **только `api`**, том БД не трогает → клиенты остаются подключёнными (проверено: после ребилда `db` = «Up N weeks», не recreated).
- `init_db()` = `create_all` (**аддитивно**, не удаляет данные). Безопасно вызывать на каждом старте.
- **ЗАПРЕЩЕНО** при правках бота: `docker compose down -v`, `DROP TABLE`, удаление тома → это сбросит привязки и заставит всех писать `/start` заново.
- Менять схему `contact_binding` — только через **`ALTER TABLE`** (create_all новые колонки не добавляет). Не «drop+recreate».

## MAX: номер телефона текстом (кнопка контакта ненадёжна)

- Кнопка `request_contact` в MAX часто **не отдаёт номер** в payload. Основной путь онбординга в MAX — **ввод номера текстом** (`max_hello_text`), кнопка оставлена как доп. вариант.
- Парсер `phone_utils.extract_phone_from_text`: терпим к `+7/8/7`, скобкам, пробелам, дефисам и **тексту вокруг** номера (phonenumbers `PhoneNumberMatcher` + regex-фоллбэк + 8→7). 10 цифр без кода → достраивается до `+7`.
- Не распознали номер → просим прислать ещё раз (`MAX_PHONE_ATTEMPTS`, счётчик в памяти), после порога — к менеджеру. Счётчик не персистится (после рестарта обнуляется — не критично).
