# Keris Server — Этап 2 «Груминг»

Источник истины бизнес-логики Keris Club (услуги, мастера, слоты, записи, абонементы).
YCLIENTS — синхронное зеркало календаря + канал карт; amoCRM — прямая интеграция.
Архитектура и контекст: [`ТЗ_ЭТАП2_ГРУМИНГ.md`](../../../04_Производство/Активные/Keris_Club/03_Проекты/Груминг/ТЗ_ЭТАП2_ГРУМИНГ.md).

## Стек

FastAPI + SQLAlchemy 2.0 + PostgreSQL (или SQLite для локальной разработки). Python 3.10+.

## Локальный запуск

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # для локали можно оставить DATABASE_URL=sqlite:///./keris_dev.db
uvicorn app.main:app --reload --port 8091
```

`GET /health` → `{"ok": true, "yclients_ready": false, "amocrm_ready": false}` пока не заданы токены.

## Деплой

VPS `194.87.118.214` (прежний `213.165.44.164` мёртв). Прод-скрипт: `deploy.py`
(нужны `KERIS_DEPLOY_HOST` и `KERIS_DEPLOY_PASSWORD` в окружении — дефолтный хост в
скрипте устарел). Сервис — `keris-server.service` (`systemctl status keris-server`),
слушает `127.0.0.1:8091`; наружу отдаётся через nginx `location /api/`, `/webhooks/`
и `/media/` на статическом сайте `keris-online-zapis/`.

`/media/` — `alias /var/lib/keris/photos/`, то есть фото до/после раздаёт nginx, а не
приложение. Каталог создаётся руками (`mkdir -p /var/lib/keris/photos`), в `.env` к нему
идут `PHOTOS_DIR` и `MEDIA_BASE_URL`.

**Telegram с RU-хоста только по IPv6.** IPv4 до `api.telegram.org` таймаутится, поэтому
в `/etc/hosts` прописан `2001:67c:4e8:f004::9 api.telegram.org`. Без этой строки хватало
не всех вызовов: `tg_http.ipv6_only` патчит `socket.getaddrinfo` глобально, и при
параллельных отправках один поток снимал патч у другого — запись создавалась, а
«спасибо за запись» падало в `ConnectTimeout`. Если Telegram сменит IPv6-адрес, строку
нужно обновить (`getent ahosts api.telegram.org` с рабочего хоста).

## API (кратко)

- `GET /api/services|addons?pet_type=dog|cat`, `GET /api/masters` (с отзывами), `GET /api/subscriptions`
- `GET /api/slots?date_iso=&service_id=&addon_ids=&master_id=&size=`
- `POST /api/bookings`
- `POST /api/bookings/{id}/reschedule` `{date_iso, time_hhmm, phone}` — перенос **той же**
  записи: мастер, услуга и длительность сохраняются, старый слот освобождается сам, второй
  записи не появляется. Меняются только дата и время; другой мастер или услуга — новая запись
- `POST /api/bookings/{id}/cancel` `{phone}` — `status=cancelled`, слот свободен, списанный
  визит абонемента возвращается на баланс (при `no_show` визит сгорает — оферта §2.4)
- Перенос и отмена требуют **телефон владельца** записи (`403` иначе): id последовательные,
  одного id мало. Заголовок `X-Admin-Key` проверку проходит без телефона и вне окна 24 ч.
  Позже `free_reschedule_hours` (24 ч) до визита клиенту — `422` с отсылкой к мастеру
- `GET /api/client?phone=` — кабинет «Мой Keris»: имя, питомцы (из истории записей),
  активный абонемент и визиты. Телефон нормализуется до `+7XXXXXXXXXX`, так что формат ввода не важен.
- `POST /api/reviews` `{phone, master_id, stars, text}` — отзыв принимается только от клиента
  с завершённым визитом у этого мастера, повторный отзыв о том же визите → 409
- `POST /webhooks/yclients` (query `?secret=` или заголовок `X-Webhook-Secret`)
- `/admin/*` — только с заголовком `X-Admin-Key`, вызывается `keris-admin-bot`

## Синхронизация

`app/sync.py`: push в YCLIENTS сразу после create/reschedule/cancel; webhook-приёмник
для записей с карт. Идемпотентность — таблица `sync_log` (уникальный `direction+event_id`).

Каталог в YCLIENTS — **своя услуга на каждый размер питомца** (без `price_min`/`price_max`
диапазона — иначе клиент с карт не может указать вес, и цена не соответствует факту).
93 позиции услуг (20 услуг × размерная сетка) + 48 позиций допов (23 фикс.-цена + 5
размерных «окрашивание»), сгруппированы по весовым категориям сетки разовых цен
(`size_grids.dogs_services`): «Собаки · до 5 кг», «5–10 кг», «10–15 кг», «15–25 кг»,
«от 25 кг», «Кошки · Короткошёрстные/Длинношёрстные (до 5 кг)» / «(от 5 кг)»,
плюс «Допы · собаки/кошки» для позиций с фикс. ценой. `Service.yclients_service_ids` /
`Addon.yclients_service_ids` — `{размер: yc_id}` (флэт-допы — ключ `"flat"`).
Обновить: `./venv/bin/python yclients_setup.py --sync-catalog`. Push уносит основную
услугу (под `booking.pet_size`) и все замапленные допы в `record.services[]`.

Обратное направление (`handle_yclients_webhook`, событие `resource=record`):

| В YCLIENTS | У нас |
|---|---|
| создана запись, которой у нас нет | `Booking(source=yclients_maps)`, услуга+допы по ID; **размер питомца — по конкретному id услуги** YCLIENTS (`Service.yclients_service_ids`), не хардкод; цена из YCLIENTS |
| create/update записи, которая у нас есть (эхо нашего пуша) | сверка времени/мастера: `unchanged` либо перенос |
| статус визита `attendance` | `-1` «Не пришел» → `no_show` (**слот освобождается**), `1` «Пришел» → `completed`, `0`/`2` → `confirmed`. По отменённой записи `0`/`2` сами по себе отмену не снимают — только вместе с переносом |
| удаление (`status=delete` или `data.deleted`) | `status=cancelled`, слот свободен, визит абонемента возвращается |
| `resource != record` | только строка в `sync_log` |

Администратор отменяет запись статусом **«Не пришел»**, а не удалением (см.
`регламент_Администратор.md`) — поэтому `attendance=-1` обязателен для маппинга: без него
запись остаётся `confirmed` и слот навсегда выпадает из онлайн-записи. В обратную сторону
наш `cancel` тоже не удаляет запись из журнала, а ставит ей «Не пришел»
(`yclients_client.mark_record_no_show`).

Из вебхука обратно в YCLIENTS не пушим — иначе цикл webhook → push → webhook.

### Доп. поля записи (кличка/порода/вес/дата рождения питомца)

С 2026-08-17 эти данные идут не в `comment`, а отдельными доп. полями записи
YCLIENTS (Настройки → Дополнительные поля → «Доп. параметры записи»). Код
каждого поля («Ключ для API») — в `.env` (`YCLIENTS_CF_PET_NAME/_BREED/_WEIGHT/
_BIRTH_DATE`). Пока код пуст, поле просто не читается/не пишется — ничего не
ломается, фича включается прописыванием кода в `.env` + `systemctl restart`.

- **Пуш к нам → в YCLIENTS** (`yclients_client.pet_custom_fields`): в
  `custom_fields` уходят только непустые значения из нашей записи; поле с пустым
  значением в payload не попадает — PUT не затирает то, что вручную заполнил
  администратор.
- **YCLIENTS → к нам** (`sync._pet_info_from_record`, читает
  `data.custom_fields`): применяется и при создании записи из вебхука/карт, и
  отдельным событием `update`, если администратор дозаполнил поля позже —
  так же, как состав услуг (`_apply_catalog_from_record`).
- `comment` в YCLIENTS теперь — только реальный текст клиента + флаги, для
  которых нет своего доп. поля (списание абонемента, отсутствие согласия на
  фото). `format_yclients_comment` в `yclients_client.py`.
- `admin_note` при создании слота с карт просит уточнить кличку/породу только
  если их не прислали доп. полями — согласия ПДн/фото доп. полями не
  покрываются, про них просим всегда.

### SMS-уведомления (targetsms.ru)

С 2026-08-24 клиентам параллельно с Telegram/MAX всегда уходит SMS через
[TargetSMS](https://targetsms.ru/support/json/): «спасибо за запись»
(`reminders.send_booking_created`) и напоминания за 24ч/3ч (`reminders.run_once`).
Не замена ботам, а независимый канал для всех клиентов, включая тех, кто бота
не привязал (раньше без привязки напоминание не отправлялось вообще —
`due_reminders` больше не фильтрует по `telegram_chat_id`/`max_user_id`).

«Любой источник» покрыт обеими точками создания записи: `POST /api/bookings`
(сайт, Mini App) и вебхук YCLIENTS (журнал администратора, Яндекс.Карты, 2ГИС) —
обе зовут `reminders.send_booking_created`. До 2026-08-24 канал жил на P1SMS,
там имя отправителя так и не прошло модерацию; модуль `p1sms_client.py` удалён.

- Выключено по умолчанию (`TARGETSMS_ENABLED=false`) — платный канал. Включается
  `TARGETSMS_ENABLED=true` + `TARGETSMS_TOKEN` в `.env`. Авторизация — заголовок
  `Authorization: Bearer <токен>`, не login/password из публичной документации
  и не пара входа в кабинет. Остальной функционал не ломается
  (`settings.targetsms_ready`, best-effort — ошибки только логируются,
  Telegram/MAX-рассылку не роняют, см. `targetsms_client.py`).
- Отправитель `KerisClub` прошёл модерацию 24.08.2026 и передаётся всегда: без
  `sender` шлюз отвечает «Нет отправителя» и в очередь сообщение не ставит.
- Один эндпоинт `sendsmsjson.php` на всё, операция задаётся полем `type`:
  `sms` (отправка), `state` (статус доставки по `id_sms`), `balance` (остаток).
  Ошибка запроса приходит как `{"error": ...}`, ошибка конкретного сообщения —
  текстом в `action` вместо `send`; клиент поднимает `TargetSMSError` в обоих
  случаях.
- Тексты (`reminders.sms_booking_created_text`/`sms_reminder_text`) — рабочие
  версии шаблонов в ЛК targetsms, с префиксом `Keris Club. ` в теле сообщения:
  именно в таком виде сообщения дошли на проверке 24.08. Формат переменных в
  шаблонах ЛК — **`%w`/`%d`, а не `{имя}`/`{дата}`** (`%w` — буквы/цифры, `%d` —
  цифры и спецсимволы; в дате `17.08 20:00` пробел маской не закрывается, поэтому
  в шаблоне два `%d`). Если текст меняется здесь — тот же шаблон нужно
  переутвердить в ЛК, иначе сообщение уходит на ручную модерацию (до 30 минут),
  что для напоминания «за 3 часа» неприемлемо.
- Вход в кабинет: `POST /api/auth/request-code` шлёт 4-значный код, `POST /api/auth/verify`
  проверяет его (TTL 10 минут, повтор не чаще раза в минуту, 5 попыток). Код
  уходит только в Telegram/MAX, SMS-канал для него не включён.
- Каждая отправка логируется с `id_sms`/`parts` — по ним видно расход, а
  `targetsms_client.get_state` разбирает жалобы «не дошло».

### Вход в кабинет: только боты

С 2026-08-20 центр тяжести уведомлений перенесён в Telegram и MAX: сообщение в
боте бесплатно, а SMS с кодом стоит как SMS о визите и нужна реже.

- `sms_otp.request_code` от SMS-канала не зависит вообще. Порядок доставки:
  Telegram (`telegram_bind.chat_id_for_phone`) → MAX (`max_bind.user_id_for_phone`).
  Текст `sms_otp.sms_otp_text` оставлен под согласованный шаблон — если решим
  включить SMS для входа, менять нужно только `_deliver`.
- Привязки нет — не ошибка, а ответ `need_bind` со ссылками на боты
  (`settings.telegram_bot_url`, `settings.max_bot_url`). Запись `SmsOtp` остаётся
  живой, `sms_otp.deliver_pending` отдаёт код сразу после привязки номера
  (вызывается из `telegram_bind.bind_client` и `max_bind.bind_client`).
- Повторный запрос в пределах минуты отдаёт `retry_after` — фронт рисует таймер,
  а не ошибку. TTL кода 600 секунд: страницу можно закрыть и вернуться.
- Подпись кода — отдельный `OTP_SECRET` в `.env`. Раньше секрет брался из ключа
  SMS-провайдера, и появление ключа обнулило бы все живые коды.

### Фото до/после

- Таблица `booking_photos` (`booking_id`, `kind` before/after, `path`, `added_at`,
  `added_by`, `sent_at`), модуль `photos.py`.
- Файл забираем себе: `getFile` отдаёт `file_path`, который живёт около часа,
  поэтому фото скачивается в `PHOTOS_DIR` (`/var/lib/keris/photos/<booking_id>/`)
  и отдаётся через nginx `location /media/` (`MEDIA_BASE_URL`). В деве есть
  фолбэк-маршрут `GET /media/{booking_id}/{filename}`.
- Приём и отправка: `POST /admin/bookings/{id}/photos`,
  `POST /admin/bookings/{id}/report/send` под `require_admin`. Клиент не в боте —
  фото сохранены, отчёт уйдёт после привязки (`photos.send_pending_reports`).
- В `GET /api/client` каждый визит получает `photos: [{kind, url}]` — история
  прошлых стрижек в кабинете не пропадает.
- Загружает администратор через отдельный сервис `keris-staff-bot`
  (`@kerisclubphotobot`, whitelist `STAFF_TELEGRAM_IDS`). Бот Карины не трогаем.

### Воронка «Груминг» в amoCRM

Каждая запись из любого канала — сделка в воронке «Груминг» (`11225138`). Модель:
контакт = владелец, Компания = питомец, сделка = один визит.

- Точка входа одна — появление `Booking` у нас: `sync.sync_booking_to_amocrm`
  зовётся из `main.create_booking`, вебхука YCLIENTS (создание, перенос, смена
  статуса, удаление), переноса, отмены, подтверждения и отправки фото-отчёта.
- Гарантия «без пропусков» — второй слой: `amocrm_stages.run_once` в
  `reminders_loop` каждые 5 минут добирает записи с пустым `amocrm_lead_id` и
  двигает этапы. Недоступность CRM в момент записи перестаёт быть потерей сделки.
- Этапы ведёт сервер, а не автоматизация amoCRM: у неё нет условия «дата визита
  наступит завтра», а время визита всё равно наше. Карта — `amocrm_stages.target_stage`:
  `Запись создана` (в сутки оформления) → `Ожидает визита` → `Завтра запись` →
  `Сегодня запись` → `Клиент пришёл` → Успех, плюс `Отменена` и `Не пришёл`.
- ID этапов и полей не хардкодятся: резолвятся по имени с кэшем на процесс
  (`amocrm_client.stage_id`, `field_id`). Воронку и поля создаёт идемпотентный
  `keris-amocrm-scripts/setup_grooming_pipeline.py`.
- Метрики клиента считаются по нашей БД и пишутся в поля контакта
  (`amocrm_metrics`): визиты, сумма, средний чек, первый/последний/следующий визит,
  статус клиента, абонемент, отмены и неявки. Режим «Покупатели» в аккаунте
  выключен, встроенного LTV нет. Статус «Спящий»/«Потерянный» меняется от времени,
  поэтому есть суточный проход `amocrm_metrics.run_daily` (04:00).
- Поиск контакта — строгий по полю `PHONE` во всех записанных форматах
  (`+7/8/7/10 цифр`). В аккаунте 250+ контактов из Wazzup, `query=`-поиск отдаёт и
  чужие карточки, поэтому результат сверяется по цифрам номера.
- Перенос истории: `amocrm_backfill.py --dry-run` печатает отчёт (сколько контактов
  найдётся, сколько создастся, на какие этапы встанут сделки), без ключа — пишет.
- 🔴 **Аккаунт amoCRM не принимает записи до оплаты подписки** (проверено
  22.08.2026): чтение, настройка воронок и полей, примечания — работают, а
  `POST /leads` отвечает `Payment Required`, `POST /contacts` и `/companies` —
  «Код ошибки 205». `amocrm_client` распознаёт это как `AmoCrmBlocked`, ставит
  паузу на 30 минут и не долбит аккаунт; записи ждут в `sync_log` со
  `reason=amocrm_blocked` и уедут в CRM первым же проходом после оплаты.

### Автоматические касания

`reminders.run_once` кроме напоминаний делает два прохода:

- **ДР питомца** — по `pet_birth_date` (день и месяц), в сам день, один раз в год.
- **«Давно не виделись»** — визита нет дольше `REACTIVATION_DAYS` (по умолчанию 60)
  и нет будущей записи; выключается `REACTIVATION_ENABLED=false`.

От повторов защищает таблица `client_outreach` (`phone`, `kind`, `tag`).

⚠️ YCLIENTS marketplace шлёт вебхуки **только** на голый `POST /webhooks/yclients`
(не доставляет `?secret=` и path-хвост `/<secret>`). Приёмник принимает голый путь
без обязательного секрета; опциональный маршрут `/webhooks/yclients/{secret}` оставлен.
В кабинете достаточно: `https://<host>/webhooks/yclients`. Диагностика:
`grep webhooks/yclients /var/log/nginx/access.log`.
Пока не заданы `YCLIENTS_USER_TOKEN`/`YCLIENTS_COMPANY_ID` (или `AMOCRM_LONG_LIVED_TOKEN`
недействителен) — запись у нас проходит нормально, push логируется как `retry`
(смотреть `sync_log.status`), исключение наружу не летит.
