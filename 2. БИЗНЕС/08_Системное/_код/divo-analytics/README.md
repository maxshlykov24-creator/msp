## Архитектура

- `api` (FastAPI) — дашборд, форма входа, `/api/daily`, `/api/meta`, `/health`.
- `worker` (APScheduler) — сбор из amoCRM по расписанию + бэкфилл истории этапов.
- `db` (PostgreSQL) — `lead_snapshot` (текущее состояние сделок), `stage_reached`
  (история этапов), `snapshot` (готовый JSON `DAILY`), `sync_state` (курсоры/ошибки).
- `nginx` (на хосте) — HTTPS + проксирование на `127.0.0.1:19100`.

Модель данных — **cohort vs outcomes** (см. `ПРОВЕРКА_ЦИФР_DIVO.md`):
- **cohort** (`traffic`, `active`, `agreed`, `tradein`, `src{}`, `stage{}`,
  `cohort_won`, `cohort_lost`) — по дате **создания** сделки, текущее состояние.
- **outcomes** (`won`, `lost`, `cash`, `invoice`, `tradein_won`, `loss{}`,
  `cycle_sum/n`) — по дате **закрытия** сделки (статус Успех/Провал).

Каждый прогон collector'а полностью пересобирает `DAILY` из хранимых снимков —
reopen, смена ответственного/источника/чекбоксов не оставляют «протухших»
цифр в старых днях.

## Схема-валидация перед каждым сбором

`app/collector.py::validate_schema()` перед КАЖДЫМ прогоном проверяет
`account_id`, воронку/статусы, ID менеджеров-пользователей и custom fields
(источник/оплата/трейд-ин/причина/согласовано) + обязательные enum-значения.
При несовпадении — collector не пишет данные, `/health` отдаёт
`schema_ok: false`, дашборд показывает баннер вместо тихого показа
устаревших цифр.

## Контроль качества звонков

Сервис `calls` получает входящие и исходящие звонки из событий и примечаний amoCRM.
Записи Mango скачиваются через проверенные хосты и обрабатываются Nexara:
`nexara-ru`, диаризация, роли, асинхронный `job_id`. Nexara делает только
транскрипт. По уточнению владельца от 08.10.2026 сохранённые тексты анализирует
отдельный агент Sonnet через существующий маршрут DIVO в OpenRouter.
Правила из фото владельца от 07.10.2026 находятся в `app/call_rules.py`.
Первичные входящие продажные разговоры оцениваются по семи критериям;
повторные, исходящие, сервисные и нецелевые получают содержание и результат без балла.
Неполные и противоречивые оценки не входят в среднее.

В БД добавляются `call_record` (уникальный звонок, связи, результат и исходный ответ)
и `call_delivery` (независимая доставка в amoCRM и Telegram).
Калибровка помечена отдельно и никогда не рассылается, даже при включённых доставках.
Коллектор продаж и `/api/daily` продолжают работать отдельно.

### Конфигурация и запуск

Все секреты только в серверном `.env`, права `600`. Пример без секретов — `.env.example`.
`CALLS_ENABLED` включает сбор; `CALLS_PROCESS_ENABLED` — платную обработку;
`CALLS_AMO_ENABLED` и `CALLS_TELEGRAM_ENABLED` — соответствующие доставки.
`CALLS_CALIBRATION_ONLY=true` разрешает платную обработку только калибровочной
выборки; рабочая очередь сохраняется. Уже созданные задания продолжают опрашиваться.
Для рабочего пилота после приёмки калибровки переключить значение в `false`.
Первое включение сбора закрепляет начало в `sync_state.calls_start_at`;
исторические звонки автоматически не подхватываются. `CALLS_START_AT` позволяет
явно установить начальную границу до первого включения.

Проверенные домены записей на текущей интеграции:
`CALLS_RECORDING_HOSTS=amocrm.mango-office.ru,files.mango-office.ru`.
Переадресация с первого домена на второй проверена на живой записи.
Произвольные хосты, приватные адреса и неаудиофайлы не принимаются.

Сотрудник определяется только по подтверждённой карте `CALLS_MANAGER_MAP`
(`source:call_responsible:amo_user_id`) либо проверенному `CALLS_VERIFIED_AUTHORS`.
Ответственный по сделке не используется. Если несколько участников/связей,
неопределённость отображается явно. Неоднозначная сделка блокирует примечание.

```bash
# Создать новые таблицы до параллельного старта контейнеров.
docker compose build api worker calls
docker compose run --rm --no-deps api python -c 'from app.database import init_db; init_db()'
docker compose up -d api worker calls

# Выбрать до 30 уникальных входящих/исходящих записей за последние 7 дней.
# Анализ выполняется только при CALLS_PROCESS_ENABLED=true.
docker compose exec -T calls python -m app.call_worker --calibrate 30

# Тесты правил, очереди, авторизации и расчётов.
docker compose exec -T api python -m unittest scripts.test_calls -v
```

Калибровку смотреть в существующем дашборде через переключатель «Калибровка».
Во вкладке «Звонки» сверху показаны сводка, выполнение критериев и менеджеры.
Ниже — список с фильтрами состояния, сотрудника, типа и сортировкой по оценке.
Клик по звонку открывает боковой разбор: критерии и цитаты, запись с поиском
по транскрипту, отдельная диагностика обработки и доставок. Калибровка отделена
от рабочих звонков; неподтверждённые оценки явно помечены как версия ИИ.
Перед рабочими доставками сверить классификацию и оценки с записью,
подтвердить карту сотрудников и конфигурацию бота/закрытой группы.
По решению владельца от 2026-10-07 отчёты направляются через существующего
`@divoalertbot` в закрытую группу «DIVO | Анализ звонков». Токен берётся из
защищённой конфигурации уведомлений DIVO; адресат анализа задаётся отдельно через
`CALLS_TELEGRAM_CHAT_ID`. Маршрут действующих уведомлений по заявкам не меняется.
Обработчик звонков использует только отправку, не запускает `getUpdates` или webhook
для общего бота и не перехватывает его входящие события.

На текущем VPS Telegram доступен по IPv6 хоста. Сервис `calls` использует
`network_mode: host`, не слушает входящие порты и подключается к PostgreSQL через
`127.0.0.1:19102`. Порт базы опубликован только на localhost; API и сборщик продаж
продолжают использовать внутреннюю Docker-сеть. До изменения сохранён `pg_dump`.
Повтор подключения допустим до отправки HTTP-запроса; ошибка чтения после POST
остаётся неоднозначной и требует ручной проверки без автоматического повторения.

Доставка в группу проверена 2026-10-07: тестовое сообщение отправлено из сервиса
`calls` и прочитано обратно из истории группы; подтверждены отправитель и текст.
Telegram-маршрут включён. Платная обработка и примечания остаются выключенными
до завершения калибровки; исторические калибровочные звонки не рассылаются.

### API и надёжность

В генерируемых сводках, объяснениях, рекомендациях, отчётах и интерфейсе название
компании пишется `DIVO MOTORS`. Частые ошибки распознавания нормализуются при
создании анализа и при выдаче старых записей. Транскрипт и дословные цитаты
доказательств сохраняются без исправлений, чтобы их можно было сверить с аудио.

Все маршруты требуют существующую сессионную авторизацию и возвращают `Cache-Control: no-store`:
`GET /api/calls`, `GET /api/calls/summary`, `GET /api/calls/{id}`,
`GET /api/calls/{id}/recording`. Подписанная ссылка Mango не отдаётся клиенту.
Фильтры: `start`, `end` (даты МСК), `manager` (user_id или `unknown`),
`category`, `calibration`; список дополнительно принимает `limit`, `offset`,
`view` (all/scored/review/unavailable/pending) и `sort` (recent/score_asc/score_desc).

Повторные события объединяются по `(account_id, uniq)`. Курсор двигается только
после полного чтения страниц. Отсутствующие записи перепроверяются отдельно
до 48 часов. Сохраняются версии правил и анализа.

При таймауте отправки в Nexara платный POST не повторяется: `submit_ambiguous`
требует проверки задания в кабинете провайдера. Сохранённый `job_id` переживает рестарт.
Для amoCRM перед POST и после него выполняется поиск маркера отчёта;
неподтверждённая запись только перепроверяется чтением. Telegram при неоднозначном
ответе получает `ambiguous`, автоматической повторной отправки нет.
Сбой одного этапа не останавливает обработку и доставку уже полученных результатов.

Диагностика: `sync_state.calls_last_error`, `calls_last_success`,
`calls_last_collection`, состояния звонков и доставок в защищённом API.
В логи не выводятся токены, подписанные URL и тексты звонков.

Откат: выключить четыре переключателя, выполнить `docker compose up -d --no-deps calls api`.
Таблицы и накопленные результаты сохраняются. Перед обновлением сохранять код
и `pg_dump`; восстановление всей базы использовать только при повреждении данных.

### Агент анализа и читаемость, 2026-10-08

Во вкладке звонков увеличены подписи, критерии, строки, цитаты и транскрипт;
размеры в продажах сохранены. Проверка интерфейса ведётся на реальной базе.

`CALLS_ANALYSIS_ENABLED` включает анализ сохранённой расшифровки агентом.
`CALLS_SONNET_API_KEY` хранится только в защищённой серверной конфигурации;
`CALLS_SONNET_MODEL` задаёт проверенный Sonnet, `CALLS_SONNET_PROXY` — маршрут при необходимости.
Агент получает только текущую расшифровку. В доказательствах он возвращает ссылки
на фрагменты: исходные цитаты и таймкоды подставляет код. Балл вычисляет прежний валидатор.
Ответ агента, модель, расход токенов и стоимость сохраняются в `provider_result.agent_result`.
Перезапуск или таймаут после POST дают `analysis_ambiguous`, без повторной оплаты автоматически.
Калибровочный переключатель блокирует анализ рабочих звонков и рассылку калибровки.

```bash
# Повторный анализ только сохранённых калибровочных текстов, без Nexara POST.
# Выполнять явно после настройки Sonnet; команда не обрабатывает рабочую историю.
docker compose exec -T calls python -m app.call_worker --reanalyze-calibration
```

Переходы: `processing` → `analysis_ready` → `analyzing` → `complete`/`needs_review`.
Сотрудник определяется по `responsible_user_id` самого примечания Mango (поле «Кому»),
после подтверждения владельцем и сверки связок в кабинете Mango. Ответственный сделки
и автор примечания не используются как замена участнику. `CALLS_VERIFIED_PARTICIPANTS`
содержит только подтверждённые ID пользователей; перевод с несколькими участниками требует проверки.
8 октября сверены четыре связки: Евгений, Никита, Эльзар, Назар.

В версии `sonnet.qa.2` после подтверждённого ответа с ошибками валидации допускается
ровно одна коррекция на той же расшифровке. Предыдущий ответ и расход сохраняются
до запроса коррекции в `provider_result.agent_attempts`. Неопределённый результат
коррекции также не повторяется автоматически. Для уже проверенной калибровки с ошибками:

```bash
docker compose exec -T calls python -m app.call_worker --repair-calibration
```

Команда пропускает результаты без ошибок и звонки с двумя сохранёнными попытками.
На сервере пройдены 47 тестов, включая сохранение первого ответа при таймауте коррекции.
