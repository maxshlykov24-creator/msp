## 1. Платный контур (факт + открытый вопрос)

**Факт:** в аккаунте много платных виджетов экосистемы F5 и смежных (чеклисты, Finder, триггеры, пушер, антидубль, правило перехода статусов и др.).

**Открытый вопрос к Сергею / биллингу amo (узнать):**
- Подписка F5 была **пакетом на много виджетов** или **поштучно**?
- Если поштучно — сколько платили за антидубль / Finder / чеклисты / пушер (мес. и суммарно за период)?
- Что ещё из платного реально включено сейчас?

→ Нужно для жёсткого аргумента в КП («уже отвалили X ₽») и для приоритета замены.

**Позиция MS Product (рабочая):** логику уведомлений и контроля SLA можно закрыть **своим ботом (Telegram / Max) + сервер**, без подписки на Finder/Pusher/часть триггеров. Чек-листы — отдельное решение (см. §4).

## 2. Finder (F5) — SLA ответа

**Назначение:** в рабочее время ответ клиенту **не дольше 15 минут**. Иначе запускается сценарий → **Триггеры**.

Цепочка уведомлений (как зафиксировал Максим):

| Шаг | Условие | Кому |
|-----|---------|------|
| 1–2 | Нет ответа 15 мин / повтор (в т.ч. логика «в течение часа») | Сотрудники (через триггеры + пушер) |
| 3 | Через **~2 часа** всё ещё проблема | **Сергей** |

**Замена (гипотеза внедрения, не обещание без скоупа):** тот же SLA → уведомления в **Telegram-бот и/или Max-бот** на наш сервер, без подписки Finder.

---

## 3. Триггеры + Пушер

Работают **в связке**. Зафиксированные сценарии:

1. **Пропущенный входящий звонок** → пушер-уведомление сотрудникам.  
2. **Нет ответа 15 мин** (из Finder) → уведомления (два «уровня» сотрудникам).  
3. **Эскалация на Сергея** (~2 часа).

По сути контур = **только уведомления** (не полноценный контроль качества переписки).  
**Замена:** бот + правила на сервере (звонок/диалог без ответа → пуш в TG/Max → эскалация владельцу).

## 4. Чек-листы F5 — механика

**Общий паттерн (факт со всех скринов):**
- Закреплено = да, цвет зелёный.
- «Записывать прогресс в поле» = **не выбрано** (прогресс в поле сделки не пишется).
- «При заполнении чек-листа» → **Сменить статус сделки = ВКЛ**.
- «Запустить сценарий в Триггерах» = обычно не выбрано.

**Следствие:** чек-лист = **шлюз этапа**. Протыкали все пункты → этап сменился сам.  
Сергей уже говорил: менеджеры тыкали вперёд. Риск подтверждён конструкцией виджета: **нет требования доказательства** (файл, письмо, факт оплаты из банка) — только галочки.

**Мнение Максима (зафиксировать):** удобно, но перегружает; часть логики можно упростить; 56 стр. инструкции менеджера — слишком тяжело для ежедневной работы (облегчать через короткие роли/бот/CRM-подсказки, не «книга»).

**Рабочая гипотеза по скоупу:** чек-листы **можно оставить** как UX-шлюз **или** заменить нативным/серверным контролем с доказательствами — решить в СКОУП_ЭТАП_1, не тащить все пункты 1:1.

## 6. Виджет «правило перехода» статусов

**Факт (разбор Максима):** виджет ограничения ручных переходов — на воронке **Новые заявки**, для этапов вроде:
- Адресная программа (руками «куда угодно» нельзя — только допустимые),
- Резерв (поставщик/клиент),
- Подготовка документов → дальше на «документы на подписи».

**Связка:** ручной хаос режут правилами перехода; **движение вперёд** в основном через **заполнение чек-листа** (автосмена статуса).  
Итого: жёсткий рельс «только вперёд через галочки» — удобно для дисциплины на бумаге, слабо против «протыкали всё».

## 7. Перегруз процесса (наблюдение для КП / TO-BE)

- Инструкция менеджера ~**56 страниц** + десятки пунктов чек-листов + таблицы + 1С + почта поставщиков + мессенджеры.
- Новичкам CRM не давали — логично: входной порог завышен.
- Цель внедрения: **не добавить ещё слой**, а **сжать** контроль в короткое действие + сигнал владельцу (бот), а длинный регламент — справочник, не ежедневное чтение.
